01

From report to code

An incoming incident report is a starting point, not a program specification. It may mix what people saw, metric values, expected behavior, guesses about the cause, and important details that are still missing.

Investigation practice / keep the source and certainty clear

Build a working explanation without turning a possible cause into a fact.

This is an investigation practice, not an instruction to delay action. During a major outage, protect users and stabilize the system first while saving logs and other data that may soon be overwritten. As the investigation proceeds, keep four things separate: what was observed, who observed it, what the system was expected to do, and what responders think may explain it.

The earlier phrase “do not strengthen the report” was trying to describe three specific mistakes that can occur when a report is restated:

Incoming claimAccidental changeWhat was lost
“The EU on-call reports 503s from two probes.”“The service is returning 503s.”The source and the limited range of the report.
“The rollout may have changed replay behavior.”“The rollout broke retries.”The uncertainty and other possible causes.
“Heap growth began after the deployment.”“The deployment caused a memory leak.”“Happened after” was changed to “caused.”

Keeping those details does not mean distrusting the reporter. It keeps the information needed to test the claim. The source tells us where to reproduce it. The reported range tells us where to look for a counterexample. Words such as “may” tell us that we have a possible cause, not a finding.

Observation

What a person or tool saw

“Probe eu-3 recorded 503 responses between 09:14 and 09:22.” Record who or what observed it and under which conditions.

Possible cause

An explanation we can test

“The rollout changed replay behavior.” State what would support it and what would show it is wrong.

Unknown

A missing fact that could change the next action

“Did first attempts fail, or only replays?” Ask first about unknowns most likely to change what you do next.

Expected

What this part of the code promises

State this in your own words before comparing it with the implementation or tests.

Record the source

Record each observation with its source, time, conditions, and reported range. Mark possible causes as such and leave unanswered questions visible.

Set the work area

Name the component and behavior you own. Record important evidence from other components without assuming that you can redesign them during this repair.

List possible causes

Keep at least two reasonable explanations in view. For each, identify an observation that would support it or show it is wrong.

Choose what to inspect

Open the smallest log, trace, test, diff, or source file that can separate the current explanations. Decide what each result would mean before opening it.

State the expected behavior

Define what this part of the code should do for the observed input. Do not assume that the current implementation is correct merely because it already exists.

Find the first wrong step

Follow the evidence to the first place actual behavior differs from expected behavior. The loudest log line may be several layers downstream.

Why this practice / lessons from safety investigations

Other fields have already learned how premature answers mislead investigations.

A software outage is not an aircraft or refinery accident. Even so, their investigators use several practices that work well for software: keep facts separate from explanations, say when the evidence is incomplete, look for evidence that could prove an early idea wrong, and look beyond the first broken part.

Stabilize, then investigate

Google SRE’s “Effective Troubleshooting” puts service restoration before root-cause work in a major outage while still preserving logs and other short-lived evidence. It starts with observations, lists possible causes, and looks for results that support or rule out each one.

Keep facts and analysis separate

The NTSB’s 2025 Alaska Airlines Flight 1282 report presents “Factual Information” before a separate “Analysis” chapter. Its timeline labels periods as undetermined when the record cannot establish the door plug’s position. It also says directly when the available data was not enough to assess Boeing’s safety culture.

Look beyond the broken part

The Chemical Safety Board’s ExxonMobil Torrance report maps causes from damaged equipment through site and corporate decisions, industry standards, and regulation. It also shows how the operating measurements people relied on failed to reveal a dangerous state.

Protect dissent from a premature conclusion

The Columbia Accident Investigation Board report describes managers converging on “no safety-of-flight” before the evidence justified it, technical concern losing urgency as it moved upward, and barriers to minority views. For a software team, the lesson is to record competing explanations and the evidence behind them.

What these reports do and do not show: they support the investigation practices above. They do not tell us what caused a particular software incident. A Wheel of Misfortune must still test each possible cause against its own metrics, logs, code, experiments, and expected behavior.

Before opening a file / ask why

Command output matters only when it changes your working understanding.

Before reading a log, diff, trace, test, or source file, write three short statements:

  1. The question: which possible cause or unanswered question is this meant to address?
  2. Why this source: how can this log, trace, test, diff, or file separate explanations that currently fit?
  3. What next: what would each possible result mean for the next action?

This feels slower for roughly a minute. It becomes much faster once the alternative is opening ten files, accumulating facts without a working explanation, and forgetting why each fact mattered.

Weak evidence request

“Show me all the logs.”

Broad inspection increases volume, not necessarily information. Prefer: “Show whether failures occurred on initial attempts, replays, or both.”

02

Code as evidence

Production code should help a responder answer four questions: what is promised, who owns it, how it fails, and when its work ends.

Pattern / show what the caller needs

Interfaces should reduce how much code a responder must read.

An interface helps during an incident when it names the one ability its caller needs. A large interface makes responders study methods that cannot affect the reported behavior.

Anti-pattern / mirrors the whole implementation
type StorageClient interface {
    Connect(context.Context) error
    Save(context.Context, *Snapshot) error
    Load(context.Context, string) (*Snapshot, error)
    Delete(context.Context, string) error
    Compact(context.Context) error
    Stats() StorageStats
    Close() error
}

type Auditor struct {
    storage StorageClient
}

The auditor appears coupled to connection management, compaction, statistics, and deletion even if it only loads one snapshot.

Pattern / says what the caller needs
// SnapshotLoader retrieves the named audit snapshot.
// It returns ErrSnapshotNotFound when no snapshot exists.
type SnapshotLoader interface {
    LoadSnapshot(
        context.Context,
        string,
    ) (*Snapshot, error)
}

type Auditor struct {
    snapshots SnapshotLoader
}

The smaller interface tells a responder which behavior matters and is easy to replace in a focused test.

During an incident / why style helps

Readable choices become incident shortcuts.

Names reduce search

LoadSnapshot distinguishes retrieval from computation. A package named snapshot says more where the code is called than util.

Errors keep the underlying cause

Wrapping an error adds the failed operation without hiding the error that the caller may need to recognize.

Report an error once

Returning an error to the code that owns the outcome prevents one failure from appearing as several separate events.

Context shows when work stops

A first-parameter context shows where cancellation begins and whether the caller’s deadline reaches the work.

Channel direction shows who can act

<-chan and chan<- show who can send and receive, which helps readers work out who must stop the work and close the channel.

Tests record expected behavior

A focused test names the input and expected result, turning a vague incident symptom into something anyone can run again.

Return context; report where the outcome is decided

Anti-pattern / one failure becomes three events
func load(ctx context.Context, id string) (*Snapshot, error) {
    value, err := store.Load(ctx, id)
    if err != nil {
        slog.Error("load failed", "id", id, "err", err)
        return nil, err
    }
    return value, nil
}
Pattern / context travels upward
func load(ctx context.Context, id string) (*Snapshot, error) {
    value, err := store.Load(ctx, id)
    if err != nil {
        return nil, fmt.Errorf("load snapshot %q: %w", id, err)
    }
    return value, nil
}

The handler, command, or supervisor that owns the outcome can now emit one structured event. The lower layer remains reusable in requests, background jobs, tests, and tools that apply different reporting policy.

04

A focused repair

An incident is urgent, but mixing the repair with cleanup, redesign, and future prevention makes the patch harder to understand and test.

Repair checklist / keep the reason for each change clear

Change only what the evidence justifies.

  1. Keep the failing example. Keep the focused test or reproduction that shows the wrong behavior.
  2. Leave nearby cleanup for later. Renames, new abstractions, formatting changes, and dependency upgrades make the important change harder to see unless the repair requires them.
  3. Repair the first wrong step. Do not compensate farther downstream merely because the symptom is louder there.
  4. Keep other errors working. Accepting one new condition must not hide unrelated failures.
  5. Say what the tests prove. A focused test supports a claim about this code. It does not prove that the entire incident is resolved.

Incident style

Small changes are easier to trust and undo.

A focused patch makes it easier to see why behavior changed, test the repair, review the risk, and revert it cleanly if the diagnosis is wrong.

Check a wider area one step at a time

1 / Exact case

Does the reported or recreated case now behave as expected?

2 / Nearby cases

Do closely related success and failure paths still behave correctly?

3 / Package tests

Do the component’s ordinary tests still pass?

4 / Running system

Do production or staging metrics support the wider claim? What is still unknown?

05

Say what remains unknown

A useful handoff separates impact, cause, repair, and verification. It tells the next responder what is known without hiding what has not been checked.

Three-minute structure / short but complete

Explain what happened and why; do not merely list commands.

Incident handoff template
Impact:
  What users or systems experienced, over what scope and time.

Confirmed scope:
  Who, where, and when was affected, and what evidence supports that statement.

Key evidence:
  The observations that separated the leading possible causes.

First wrong step:
  The earliest place in code we own where behavior became wrong.

Repair:
  The exact behavior change and why it fixes the problem.

Verification:
  Focused reproduction, neighboring cases, and broader checks.

Still unknown:
  What has not been checked or belongs to another component.

Preventive follow-up:
  One test, release check, metric, or log improvement.

Avoid

  • “Fixed” without naming the confirmed scope.
  • A command transcript with no explanation of what each result established.
  • Mixing up the visible symptom, the defect in this code, and the wider incident.
  • Claiming another component behaved a certain way without evidence.
  • A prevention backlog disguised as part of the emergency repair.
06

Write for the next incident

The repair closes one defect. The lesson lasts only when the codebase makes a similar incident easier to understand next time.

Prevention / keep what we learned

Put each production lesson somewhere it will be used.

Focused test

Record the expected behavior in the smallest part of the code that owns it. Include important error cases and, when relevant, more than one implementation.

Release check

Run the test where risky changes enter: a new adapter, migration, small canary rollout, or compatibility test.

Metrics and logs

Add signals that separate the main possible causes. Use a few useful labels rather than a flood of messages.

API comment

Put responsibility for starting and stopping work, cancellation, and unusual behavior beside the API so responders do not need to rely on team memory.

Incident note

Record the surprising cause and the shortest useful path to finding it, without turning ordinary code comments into a postmortem.

Closure / one alert, two responders

The end of each alert response is a deployment.

The deployment does not always change business logic. It may add a focused test, a worker-lifecycle metric, a typed error, a diagnostic endpoint, a clearer API, or a better alert. If an incident exposes a question that our code cannot answer, changing only the alert threshold leaves the next responder with the same question.

This does not mean changing code for its own sake. Close the response by asking what small, reviewable change will preserve what the team learned. If the alert was wrong, change its threshold or routing. If the system could not separate plausible causes, add the signals it lacked. If hidden state or ownership caused the confusion, fix the design.

Before / hidden lifetime and reused cancellation
type Pool struct {
    ctx    context.Context
    cancel context.CancelFunc
    queue  Queue
}

func (p *Pool) Reload() {
    p.cancel()
    p.start(p.ctx)
}

func (p *Pool) start(ctx context.Context) {
    go func() {
        for {
            select {
            case <-ctx.Done():
                return
            case job := <-p.queue.Ready():
                if err := handle(ctx, job); err != nil {
                    p.queue.Retry(job)
                }
            }
        }
    }()
}

The replacement receives the same context that cancel just cancelled, so it exits immediately. The API exposes no way to wait for workers, inspect why they stopped, or count attempt outcomes.

After / explicit ownership, outcomes, and evidence
func (s *Supervisor) Reload(parent context.Context) error {
    if err := s.stopAndWait(ErrReloaded); err != nil {
        return fmt.Errorf("stop worker generation: %w", err)
    }

    ctx, cancel := context.WithCancelCause(parent)
    done := make(chan error, 1)
    s.cancel, s.done = cancel, done

    go func() { done <- s.worker.Run(ctx) }()
    return nil
}

func (w *Worker) Run(ctx context.Context) (runErr error) {
    w.observe.WorkerStarted()
    defer func() {
        cause := classifyStop(runErr, context.Cause(ctx))
        w.observe.WorkerStopped(cause)
    }()

    for {
        select {
        case <-ctx.Done():
            return context.Cause(ctx)
        case job := <-w.queue.Ready():
            started := time.Now()
            err := w.handle(ctx, job)
            outcome := classifyOutcome(err)
            w.observe.AttemptFinished(outcome, time.Since(started))

            if retryable(err) {
                w.observe.RetryScheduled(classifyRetry(err))
                w.queue.Retry(job)
            }
        }
    }
}

The supervisor creates a fresh context, owns cancellation, and waits for the previous workers to stop. The worker records a finite outcome value after each attempt.

The example is deliberately simplified. Production code must define what happens when the queue closes and how it handles successful jobs and permanent failures. It must also decide whether a reload may pause consumption or safely overlap worker generations. The new API makes those choices visible instead of hiding them inside start.

A small observation interface used by the queue and workers
type WorkObserver interface {
    Enqueued()
    WorkerStarted()
    WorkerStopped(StopCause)
    AttemptFinished(Outcome, time.Duration)
    RetryScheduled(RetryReason)
}

The queue calls Enqueued after it accepts a job. Workers report when they start and stop, how each attempt ends, and why they schedule a retry. A metrics adapter turns those finite values into counters, gauges, and histograms. Tests use a recording observer to verify the reload sequence.

Responder responsibility

  • State the competing explanations and the evidence that would distinguish them.
  • Review generated code for correct concurrency, shutdown, error handling, privacy, and performance.
  • Reject instrumentation that has no operational question or uses unbounded labels.
  • Run focused tests before using production telemetry to make a broader claim.

Code-generation tools make a broader response practical. They can draft the repetitive parts of an observation interface, metrics adapter, test matrix, dashboard query, and runbook change together. They cannot decide what the system needs to prove. The responder defines the required evidence and verifies that the generated code produces it.

The expanded style guide provides the building blocks for this design. They include explicit goroutine lifetime and cancellation, errors that preserve their cause, small interfaces defined by their users, and tests that wait for observable completion. Reliability architecture uses those building blocks to decide which state must be visible, who owns it, and which signals will distinguish plausible failures.

07

Release and deploy safely

A repair is not finished when it compiles. We also need a controlled way to put it into service, see unexpected changes quickly, and return to a known-good state.

Release engineering / make safe behavior routine

Deploying code and activating behavior are different operations.

Software has to change. The practical aim is not to avoid releases, but to make ordinary releases small enough to observe and easy enough to stop. Sarah Murphy’s Principles of Release Engineering describes this in terms of preserving a known-good state, rolling out changes in stages, reducing the time and attention required to ship, and treating unexpected production changes as bugs.

DeployPut the new version in place.

The binary can contain both the established and new behavior while production continues to use the established path.

ActivateChoose who receives the change.

A feature flag, canary, region, or traffic rule lets the team increase exposure deliberately.

ObserveKnow what must remain healthy.

Compare errors, latency, resource use, and the important user action against the state before activation.

ReverseDecide how to get back first.

Turning off a flag or routing traffic back is safer than inventing a repair while the impact is growing.

Keep the established path available during rollout

A simplified application gate
type Searcher interface {
    Find(context.Context, string) ([]Result, error)
}

type Rollout interface {
    Enabled(feature, subject string) bool
}

type SearchHandler struct {
    established Searcher
    candidate   Searcher
    rollout     Rollout
}

func (h *SearchHandler) searcherFor(accountID string) Searcher {
    if h.rollout.Enabled("search-v2", accountID) {
        return h.candidate
    }
    return h.established
}

Shipping this binary does not require enabling search-v2. Activation can begin with a small group, stop without another build, and retain the established path until the candidate has proved safe.

Production example / Grafana Cloud, February 2025

A narrow test passed; the full deployment failed.

A TLS-policy override remained in place after configuration reconciliation in development. A complete redeployment was not tested. When the merge-policy change reached every environment together, it also changed Kubernetes Services from LoadBalancer to ClusterIP, causing Kubernetes to destroy the load balancers.

Summary of Grafana Labs’ public incident report
Test the whole change

Confirm the result after creating or replacing the managed resource, not only after updating one field on a resource that already exists.

Enforce the first wave

Make development the default first destination. Reaching staging or production together should require an explicit exception.

Hold and compare

After each wave, check the expected change and unrelated critical behavior. A healthy process is not enough if a load balancer or another external resource disappeared.

Stop on an unexpected change

Rollback or deactivate first when that is safe. Investigate after impact has stopped growing and evidence has been preserved.

Plan stored-state changes separately

A binary can often be rolled back; a schema, membership record, or destructive external action may not be. Such changes need their own staged compatibility and recovery plan.

08

Wheels of Misfortune

Fourteen short investigations draw on production reports, security advisories, and open-source changes. They provide new Go examples for practicing how to read reports and choose useful evidence, without repeating the bugs in go-crucible’s numbered exercises.

How to use sources

Common bug patterns give us leads, not proof.

A short list of goroutine leak patterns can help at the start of an investigation. It gives a responder names for blocked sends, missing cancellation, and untracked work. It does not show which one, if any, caused this incident.

Check even familiar examples against the Go specification. A receive from a closed channel is ready immediately; without the two-value receive it can create a hot loop rather than a blocked goroutine. A channel buffer can delay a blocked send without deciding who must receive it. A WaitGroup can wait for completion, but cannot cancel the work.

Source trail

Follow the work from report to test.

Original report → design or Kubernetes Enhancement Proposal (KEP) → implementation PR → compatibility tests → benchmark. Each source answers a different question. If they disagree, investigate the difference.

How to read the debriefs: cause, repair, and reported-result statements summarize the linked sources. Labels beginning with “Suggested” and the broader prevention or release lessons are teaching inferences unless the text explicitly attributes them to a report, test, or pull request.

Open debrief — cause, repair, and prevention

Cause: request count hid the size of each request. A low-rate client could send a batch large enough to create thousands of cache operations at once. Those connections consumed ephemeral ports. Because all cache calls shared those ports, unrelated paths also failed. Logging every failure then made the overloaded process do even more work.

Suggested verification: exercise the largest supported batch; assert the concurrency ceiling; cancel while submissions are waiting for capacity; confirm each newly admitted task observes the canceled context before starting dependency work; and verify that the same logical results are returned. func writeItems[T any](w io.Writer, items []T) error {
    if _, err := io.WriteString(w, `{"items":[`); err != nil {
        return fmt.Errorf("write list prefix: %w", err)
    }
    for index := range items {
        if index > 0 {
            if _, err := io.WriteString(w, ","); err != nil {
                return fmt.Errorf("write item separator: %w", err)
            }
        }
        encoded, err := json.Marshal(items[index])
        if err != nil {

        }
        if _, err := w.Write(encoded); err != nil {
            return fmt.Errorf("write item %d: %w", index, err)
        }
    }
    if _, err := io.WriteString(w, `]}`); err != nil {

    }

}

Wheel of Misfortune H / The Replicas That Agreed

Every copy can agree that live data is gone.

The table has long runs of deleted sequential keys and occasionally receives corrections in old key ranges. Near the missing write, multi-version concurrency control (MVCC) garbage collection and a range split ran at nearly the same time.

Teaching report — reconstructed from CockroachDB Technical Advisory 162085

CockroachDB divides its ordered keys into ranges and keeps several copies of each range. MVCC retains old versions of a key so transactions can read a consistent point in time; garbage collection later removes versions that are no longer needed. For a long span of obsolete keys, a range tombstone can delete the span more efficiently than deleting keys one at a time. A latch is a short-lived internal lock that prevents conflicting operations on the same keys.

Do not equate agreement with correctness

What operation could reach every copy?
  • Garbage collection found at least 2,000 consecutive obsolete versions.
  • The range split inside that span while the request was being prepared.
  • A new write landed on the new right-hand range before clearing finished.
  • The clear operation was created by the old left-hand range.

Choose the next evidence

Compare the advertised span with the actual deletion.
  1. Build a timeline of GC, the split, and the new write.
  2. Record the range bounds used to route and latch the request.
  3. Record every key span the request will actually clear.
  4. Check whether the two spans are validated together after the split.

Simplified Go model — not CockroachDB source

Coordination follows the header; deletion follows another span
type ClearRequest struct {
    Header Span
    Clear  Span
}

    release := r.latches.Lock(req.Header)
    defer release()

    if !r.bounds().Contains(req.Header) {
        return ErrRangeChanged
    }
    return r.store.Clear(req.Clear)
}
Open debrief — cause, repair, and why checks could miss it

Cause: GC identified a clearable span before a split. After the split, the request header described the left-hand range, but the ClearRange operation could still extend into the new right-hand range. Latches protected only the advertised left-hand work. A right-hand write could therefore succeed and then be removed when the old clear operation reached the same underlying storage.

Validate and protect the keys that will actually be cleared

    release := r.latches.Lock(req.Clear)
    defer release()

    current := r.bounds()
    if !current.Contains(req.Clear) {
        return ErrRangeChanged
    }
    return r.store.Clear(req.Clear)
}

Repair: CockroachDB added checks for GC keys that straddle the request header and tightened how the request span is constructed and validated. The exact production repair is more defensive than the sketch above; the important rule is that routing, latching, validation, and storage must describe the same keys.

Why replicas could agree: after a split, the left- and right-hand ranges can still share the same storage on a node. Applying the same range tombstone on the left-hand replicas can therefore delete the right-hand key on every replica. Agreement proves that the same operation ran; it does not prove that the operation was valid.

Detection: a secondary index may retain evidence that the primary row disappeared, and some timing variants can make replicas diverge. Neither is guaranteed. The advisory therefore recommends patched releases rather than relying on detection alone.

Suggested verification: reproduce all three required events—an eligible obsolete span, a split inside it, and a new write on the right before clearing completes. Assert that an old request is rejected or rebuilt and that the new write survives.

Source trail: the CockroachDB advisory gives the required timing, affected versions, mitigations, detection limits, and technical sequence. Open debrief — cause, repair, and evidence

Cause: two optimizer rules were correct for an established index. If an update did not change index columns, the plan could avoid fetching them and avoid writing the unchanged index entry.         plan.skipPartialIndexWrite()

A conditional copy leaves the client’s value in place
func copyIdentity(
    request *http.Request,
    authResponse *http.Response,
    headers []string,
) {
    for _, name := range headers {
        if value := authResponse.Header.Get(name); value != "" {
            request.Header.Set(name, value)
        }
    }
}
Open debrief — cause, repair, and trust-boundary test

Cause: Caddy’s forward_auth copy_headers handling replaced a request header only when the authentication response supplied a value. If the response omitted the header, Caddy skipped the replacement and left the client’s value in place. The change that introduced this regression was intended to avoid copying empty placeholder values.

Remove untrusted state before conditionally adding trusted state
func copyIdentity(
    request *http.Request,
    authResponse *http.Response,
    headers []string,
) {
    for _, name := range headers {
        request.Header.Del(name)
        if value := authResponse.Header.Get(name); value != "" {
            request.Header.Set(name, value)
        }
    }
}

Repair: Caddy now deletes every header named in copy_headers before it conditionally copies the authentication service’s value. If the service returns a value, the backend receives that trusted value. If it returns nothing, the backend receives no header.

Suggested verification: send an authenticated request with a forged identity header while the authentication response omits that header; assert that the backend receives no value. Then have the authentication service return an authoritative value and assert that it replaces the client’s value. Test both same-name copies and renamed destination headers.

Teaching inference: absence matters at a trust boundary. Removing untrusted data and adding trusted data are separate operations. Remove the client’s value first; then decide whether an authoritative source should replace it.

Source limit: the advisory and pull request document the vulnerability, the change that introduced it, the affected versions, and the repair. They do not report exploitation in the wild.

Source trail: the advisory explains how a caller with a valid credential could preserve forged identity headers and identifies the regression. The repair PR adds the unconditional deletion, along with configuration and integration tests. Read Caddy advisory GHSA-7r4p-vjf4-gxv4, introducing PR #6608, and repair PR #7545.

Wheel of Misfortune K / Two Paths for One Request

The router authorizes one path, but the backend receives another.

Canonical request identityAdvancedSource: May 202530 minutes

A proxy exposes /public through one router and protects another path with different middleware. A request containing percent-encoded dot segments matches the public route. The backend later interprets the path differently and serves a resource that was not meant to be public.

Teaching report — reconstructed from Traefik advisory GHSA-vrch-868g-9jx5

Name every representation

What does each component believe the path is?
  • The raw request contains percent-encoded characters.
  • The router uses one path to match its rules.
  • That match determines which middleware runs.
  • The backend interprets the forwarded path.

Choose the decisive trace

Compare policy input with execution input.
  1. Record the raw and decoded request path.
  2. Record the path used to choose the router.
  3. Record which middleware chain ran.
  4. Record the path ultimately forwarded downstream.

Simplified Go router — not Traefik source

Routing and forwarding interpret the path differently
func serve(request *http.Request) error {
    route := matchRoute(request.URL.EscapedPath())

    forwardedPath := path.Clean(request.URL.Path)
    return route.Forward(request.Context(), forwardedPath)
}
Open debrief — cause, repair, and boundary tests

Cause: Traefik did not use the same canonical path for matching and forwarding. The encoded path could select a router before Traefik removed dot segments or decoded unreserved characters. The backend then received a path with a different meaning, so the middleware chosen for the first path did not necessarily protect the second.

Canonicalize once before routing policy
func serve(request *http.Request) error {
    routingPath, forwardedPath, err := canonicalPaths(request.URL)
    if err != nil {
        return fmt.Errorf("canonicalize request path: %w", err)
    }

    route := matchRoute(routingPath)
    return route.Forward(request.Context(), forwardedPath)
}

Repair: before routing, Traefik now decodes unreserved characters, normalizes the case of percent escapes, removes dot segments, and merges repeated slashes. It stores the resulting routing path in the request context. A follow-up changed the v3 matchers to use that path too.

Suggested verification: exercise literal and encoded dot segments, upper- and lower-case percent escapes, repeated slashes, and reserved characters. Assert not only the status code but also the selected router, middleware chain, and forwarded path.

Teaching inference: every component that makes a security decision must agree about which resource a request names. Validating one representation and acting on another creates a policy bypass, even when each transformation seems reasonable by itself.

Source limit: the advisory provides a proof of concept and lists affected releases. It does not report exploitation in the wild or a public outage.

Source trail: the advisory demonstrates the middleware bypass with an encoded traversal. The v2 repair adds path normalization and sanitization before routing. The v3 follow-up makes its matchers use the same routing path. Read Traefik advisory GHSA-vrch-868g-9jx5, repair PR #11768, and v3 follow-up PR #11790.

Wheel of Misfortune L / The Neighbor’s ServiceEntry

A global hostname map erases a namespace boundary.

Multi-tenant configurationAdvancedSource: April–July 201930 minutes

Two teams define the same external hostname in separate Kubernetes namespaces. One team expects its ServiceEntry to remain local, but proxies in the other namespace begin sending requests to the first team’s destination. A related conflict causes HTTP 503 responses from an internal service.

Teaching report — reconstructed from Istio issue #13008

Look for a lost part of identity

Which fields distinguish the two declarations?
  • The hostname is deliberately the same.
  • The namespace and export scope are different.
  • The destination endpoints can be different.
  • The proxy that will use the entry has its own namespace and import scope.

Vary order and point of view

Does resolution depend on who asks?
  1. Create the entries in both possible orders.
  2. Resolve the hostname from a proxy in each namespace.
  3. Record the endpoints and cluster configuration delivered to each proxy.
  4. Repeat with explicit local and cross-namespace imports.

Simplified Go registry — not Istio source

The map key drops the namespace
type Registry struct {
    endpoints map[string][]Endpoint
}

func (r *Registry) Add(entry ServiceEntry) {
    r.endpoints[entry.Host] = append(
        r.endpoints[entry.Host],
        entry.Endpoints...,
    )
}

func (r *Registry) Resolve(_ Proxy, host string) []Endpoint {
    return r.endpoints[host]
}
Open debrief — cause, repair, and isolation contract

Cause: Pilot used the hostname alone as a service’s global identity. But namespace visibility also determined which ServiceEntry a proxy could use. With duplicate hostnames, some code paths chose a namespace arbitrarily while others combined services. Resolution did not consistently use the requesting proxy’s Sidecar scope.

Resolve within the requesting proxy’s visible configuration
type ServiceKey struct {
    Namespace string
    Host      string
}

type Registry struct {
    endpoints map[ServiceKey][]Endpoint
}

func (r *Registry) Resolve(proxy Proxy, host string) []Endpoint {
    for _, namespace := range proxy.ImportedNamespaces() {
        key := ServiceKey{Namespace: namespace, Host: host}
        if endpoints := r.endpoints[key]; len(endpoints) != 0 {
            return endpoints
        }
    }
    return nil
}

Repair: Istio changed Pilot to resolve duplicate hostnames through the requesting proxy’s Sidecar scope. Where possible, it prefers the proxy’s own namespace. The PR also added an integration test. The real implementation handles more resolution modes than the sketch above.

Suggested verification: create duplicate DNS and static ServiceEntries in several namespaces, vary their creation order, and inspect the configuration delivered to proxies with different scopes. Assert deterministic results and confirm that a local entry cannot affect an unrelated namespace.

Teaching inference: namespace, tenant, account, region, and environment are not mere metadata when they control visibility. Include those fields in lookup, merge, cache, and deduplication keys.

Source limit: the issue includes a concrete multi-namespace reproduction and shows how the conflict could disrupt production traffic. It does not describe the size or duration of a public outage.

Source trail: the issue shows cross-namespace routing interference, arbitrary endpoint selection, and a conflict with an internal service. The repair PR explains the previous undefined behavior, introduces Sidecar-scoped resolution, and adds integration coverage. Read Istio issue #13008 and repair PR #13631.

Wheel of Misfortune M / The Rebalance That Overwrote Its Source

Stopping work does not make every old worker harmless.

Stale asynchronous workAdvancedSource: August 202430 minutes

An object-store cluster has several storage pools. An operator repeatedly starts and stops rebalancing while workers move existing objects. After the sequence, some objects are unreadable even though the stop commands have returned.

Teaching report — reconstructed from the MinIO repair PR’s reproduction

Find what outlives the command

Which decisions happen at different times?
  • The worker chooses its source pool when it starts.
  • An operator can stop or restart rebalancing while it runs.
  • The write path chooses a destination later.
  • The old worker may still reach that write after the stop.

Inspect the commit boundary

What must still be true immediately before writing?
  1. Record the worker’s original source pool.
  2. Record the selected destination pool.
  3. Record which rebalance run created the worker.
  4. Reject the move if its source and destination are the same.

Simplified Go worker — not MinIO source

Destination selection forgets where the data came from
type Move struct {
    Object Object
    Source int
}

func (s *Store) apply(move Move) error {
    destination := s.choosePool(move.Object)
    return s.pools[destination].Put(move.Object)
}
Open debrief — cause, repair, and stale-work test

Cause: stopping a rebalance could race with workers that were already moving data. A worker could later choose the same pool it had read from as its destination. Treating that as a normal move allowed the write to overwrite the source object.

Carry the source identity to the final precondition
var ErrSamePool = errors.New("source and destination pool are the same")

func (s *Store) apply(move Move) error {
    destination := s.choosePool(move.Object)
    if destination == move.Source {
        return ErrSamePool
    }
    return s.pools[destination].Put(move.Object)
}

Repair: MinIO now carries SrcPoolIdx through normal and multipart data-movement writes. PutObject and NewMultipartUpload reject a write when the destination pool matches the source. They return a specific data-movement overwrite error, which the rebalance worker treats as an expected result of racing with a stop.

Suggested verification: place a test barrier after reading from the source but before destination selection, stop and restart rebalance, and then release the stale worker. Assert that self-targeting movement is rejected and that every object remains readable. Also cover multipart objects.

Teaching inference: cancellation asks work to stop; it does not prove that every worker has stopped. Destructive background work should carry its source pool—and, when needed, a run ID—all the way to the write. It must then check that the operation is still valid.

Source limit: the PR provides the production repair and a repeatable start/stop stress test. It does not link to a separate operator report or public outage.

Source trail: the PR describes the stop race, carries the source-pool index through each write path, and rejects moves back to the source pool. Its test recipe repeatedly starts and stops rebalancing, then checks that every object remains readable. Read MinIO repair PR #20233.

Wheel of Misfortune N / The Three-Day Delete

A cheap durability step becomes a multi-day delay when repeated millions of times.

Durability boundariesIntermediateSource: January 202625 minutes

Retention-policy deletion appears to hang on databases with more than ten million series. The process stays alive and the disk remains busy, but deletion makes almost no visible progress. At roughly 35 million series, the measured cost per series predicts several days of work.

Teaching report — reconstructed from InfluxDB PR #27114

Multiply the local cost

What happens once per series?
  • Each deletion acquires a partition mutex.
  • It records one series as deleted.
  • It flushes the active segment with fsync.
  • The loop runs millions of times alongside other disk I/O.

Measure work, not liveness

Which evidence distinguishes deadlock from slow progress?
  1. Count series completed and remaining.
  2. Measure time per logical deletion and per flush.
  3. Record mutex wait and disk latency separately.
  4. Project completion time at production cardinality.

Simplified Go deletion — not InfluxDB source

Every logical deletion becomes a durability barrier
func (f *SeriesFile) Delete(ids []uint64) error {
    for _, id := range ids {
        partition := f.partitionFor(id)
        if err := partition.DeleteSeriesID(id); err != nil {
            return err
        }
        if err := partition.Flush(); err != nil {
            return err
        }
    }
    return nil
}
Open debrief — cause, repair, and durability contract

Cause: DeleteSeriesID held a mutex and flushed its segment for every ID. The PR measured about 7.5 milliseconds per deletion in one test. At roughly 35 million series, that rate predicts almost three days of work—even before production lock contention and competing disk I/O.

Record the batch, then flush each touched partition
func (f *SeriesFile) Delete(ids []uint64) error {
    touched := make(map[int]struct{})
    for _, id := range ids {
        partition, err := f.DeleteSeriesID(id, NoFlush)
        if err != nil {
            return err
        }
        touched[partition.ID()] = struct{}{}
    }
    return f.FlushSegments(touched)
}

Repair: InfluxDB made deletion and flushing separate operations. Bulk deletion records which partitions it touched, then flushes each partition’s active segment once, running those flushes in parallel. The change also logs progress every 10,000 series. In the revised test, the PR reports roughly two milliseconds for 10,000 deletions.

Suggested verification: use a fake segment that counts flushes. Delete IDs spanning several partitions, then assert one final flush per touched partition rather than one per ID. Reopen the series file and confirm deletions remain durable. Benchmark at realistic cardinality rather than extrapolating from a small fixture alone.

Teaching inference: durability needs an explicit boundary. Calling fsync after every small change is easy to reason about, but a batch can preserve the same recovery guarantee with far fewer flushes.

Operational lesson: progress logs let responders distinguish a deadlock from slow forward progress. They also reveal the likely completion time while the team evaluates a deeper repair.

Source trail: the PR describes the high-cardinality trigger, measures the cost per series, projects the multi-day runtime, and implements batched flushing and progress logs. It also tests deletion with and without an immediate flush. Read InfluxDB repair PR #27114.
