Code Under Pressure

We write production code to be analyzed under time pressure, during incident response. This is why the style guide matters. Concretely:

  • Namesmake code searches faster.
  • Contractsshow what the code promises to do.
  • Error chainsshow what failed underneath.
  • Ownershipshows who must act and where to make the repair.
  • Cancellationshows when background work should stop.
  • Testskeep the same bug from returning.

01

From report to code

An incoming incident report is a starting point, not a program specification. It may mix what people saw, metric values, expected behavior, guesses about the cause, and important details that are still missing.

Investigation practice / keep the source and certainty clear

Build a working explanation without turning a possible cause into a fact.

This is an investigation practice, not an instruction to delay action. During a major outage, protect users and stabilize the system first while saving logs and other data that may soon be overwritten. As the investigation proceeds, keep four things separate: what was observed, who observed it, what the system was expected to do, and what responders think may explain it.

The earlier phrase “do not strengthen the report” was trying to describe three specific mistakes that can occur when a report is restated:

Incoming claimAccidental changeWhat was lost
“The EU on-call reports 503s from two probes.”“The service is returning 503s.”The source and the limited range of the report.
“The rollout may have changed replay behavior.”“The rollout broke retries.”The uncertainty and other possible causes.
“Heap growth began after the deployment.”“The deployment caused a memory leak.”“Happened after” was changed to “caused.”

Keeping those details does not mean distrusting the reporter. It keeps the information needed to test the claim. The source tells us where to reproduce it. The reported range tells us where to look for a counterexample. Words such as “may” tell us that we have a possible cause, not a finding.

Observation

What a person or tool saw

“Probe eu-3 recorded 503 responses between 09:14 and 09:22.” Record who or what observed it and under which conditions.

Possible cause

An explanation we can test

“The rollout changed replay behavior.” State what would support it and what would show it is wrong.

Unknown

A missing fact that could change the next action

“Did first attempts fail, or only replays?” Ask first about unknowns most likely to change what you do next.

Expected

What this part of the code promises

State this in your own words before comparing it with the implementation or tests.

Record the source

Record each observation with its source, time, conditions, and reported range. Mark possible causes as such and leave unanswered questions visible.

Set the work area

Name the component and behavior you own. Record important evidence from other components without assuming that you can redesign them during this repair.

List possible causes

Keep at least two reasonable explanations in view. For each, identify an observation that would support it or show it is wrong.

Choose what to inspect

Open the smallest log, trace, test, diff, or source file that can separate the current explanations. Decide what each result would mean before opening it.

State the expected behavior

Define what this part of the code should do for the observed input. Do not assume that the current implementation is correct merely because it already exists.

Find the first wrong step

Follow the evidence to the first place actual behavior differs from expected behavior. The loudest log line may be several layers downstream.

Why this practice / lessons from safety investigations

Other fields have already learned how premature answers mislead investigations.

A software outage is not an aircraft or refinery accident. Even so, their investigators use several practices that work well for software: keep facts separate from explanations, say when the evidence is incomplete, look for evidence that could prove an early idea wrong, and look beyond the first broken part.

Stabilize, then investigate

Google SRE’s “Effective Troubleshooting” puts service restoration before root-cause work in a major outage while still preserving logs and other short-lived evidence. It starts with observations, lists possible causes, and looks for results that support or rule out each one.

Keep facts and analysis separate

The NTSB’s 2025 Alaska Airlines Flight 1282 report presents “Factual Information” before a separate “Analysis” chapter. Its timeline labels periods as undetermined when the record cannot establish the door plug’s position. It also says directly when the available data was not enough to assess Boeing’s safety culture.

Look beyond the broken part

The Chemical Safety Board’s ExxonMobil Torrance report maps causes from damaged equipment through site and corporate decisions, industry standards, and regulation. It also shows how the operating measurements people relied on failed to reveal a dangerous state.

Protect dissent from a premature conclusion

The Columbia Accident Investigation Board report describes managers converging on “no safety-of-flight” before the evidence justified it, technical concern losing urgency as it moved upward, and barriers to minority views. For a software team, the lesson is to record competing explanations and the evidence behind them.

What these reports do and do not show: they support the investigation practices above. They do not tell us what caused a particular software incident. A Wheel of Misfortune must still test each possible cause against its own metrics, logs, code, experiments, and expected behavior.

Before opening a file / ask why

Command output matters only when it changes your working understanding.

Before reading a log, diff, trace, test, or source file, write three short statements:

  1. The question: which possible cause or unanswered question is this meant to address?
  2. Why this source: how can this log, trace, test, diff, or file separate explanations that currently fit?
  3. What next: what would each possible result mean for the next action?

This feels slower for roughly a minute. It becomes much faster once the alternative is opening ten files, accumulating facts without a working explanation, and forgetting why each fact mattered.

Weak evidence request

“Show me all the logs.”

Broad inspection increases volume, not necessarily information. Prefer: “Show whether failures occurred on initial attempts, replays, or both.”

02

Code as evidence

Production code should help a responder answer four questions: what is promised, who owns it, how it fails, and when its work ends.

Pattern / show what the caller needs

Interfaces should reduce how much code a responder must read.

An interface helps during an incident when it names the one ability its caller needs. A large interface makes responders study methods that cannot affect the reported behavior.

Anti-pattern / mirrors the whole implementation
type StorageClient interface {
    Connect(context.Context) error
    Save(context.Context, *Snapshot) error
    Load(context.Context, string) (*Snapshot, error)
    Delete(context.Context, string) error
    Compact(context.Context) error
    Stats() StorageStats
    Close() error
}

type Auditor struct {
    storage StorageClient
}

The auditor appears coupled to connection management, compaction, statistics, and deletion even if it only loads one snapshot.

Pattern / says what the caller needs
// SnapshotLoader retrieves the named audit snapshot.
// It returns ErrSnapshotNotFound when no snapshot exists.
type SnapshotLoader interface {
    LoadSnapshot(
        context.Context,
        string,
    ) (*Snapshot, error)
}

type Auditor struct {
    snapshots SnapshotLoader
}

The smaller interface tells a responder which behavior matters and is easy to replace in a focused test.

During an incident / why style helps

Readable choices become incident shortcuts.

Names reduce search

LoadSnapshot distinguishes retrieval from computation. A package named snapshot says more where the code is called than util.

Errors keep the underlying cause

Wrapping an error adds the failed operation without hiding the error that the caller may need to recognize.

Report an error once

Returning an error to the code that owns the outcome prevents one failure from appearing as several separate events.

Context shows when work stops

A first-parameter context shows where cancellation begins and whether the caller’s deadline reaches the work.

Channel direction shows who can act

<-chan and chan<- show who can send and receive, which helps readers work out who must stop the work and close the channel.

Tests record expected behavior

A focused test names the input and expected result, turning a vague incident symptom into something anyone can run again.

Return context; report where the outcome is decided

Anti-pattern / one failure becomes three events
func load(ctx context.Context, id string) (*Snapshot, error) {
    value, err := store.Load(ctx, id)
    if err != nil {
        slog.Error("load failed", "id", id, "err", err)
        return nil, err
    }
    return value, nil
}
Pattern / context travels upward
func load(ctx context.Context, id string) (*Snapshot, error) {
    value, err := store.Load(ctx, id)
    if err != nil {
        return nil, fmt.Errorf("load snapshot %q: %w", id, err)
    }
    return value, nil
}

The handler, command, or supervisor that owns the outcome can now emit one structured event. The lower layer remains reusable in requests, background jobs, tests, and tools that apply different reporting policy.

04

A focused repair

An incident is urgent, but mixing the repair with cleanup, redesign, and future prevention makes the patch harder to understand and test.

Repair checklist / keep the reason for each change clear

Change only what the evidence justifies.

  1. Keep the failing example. Keep the focused test or reproduction that shows the wrong behavior.
  2. Leave nearby cleanup for later. Renames, new abstractions, formatting changes, and dependency upgrades make the important change harder to see unless the repair requires them.
  3. Repair the first wrong step. Do not compensate farther downstream merely because the symptom is louder there.
  4. Keep other errors working. Accepting one new condition must not hide unrelated failures.
  5. Say what the tests prove. A focused test supports a claim about this code. It does not prove that the entire incident is resolved.

Incident style

Small changes are easier to trust and undo.

A focused patch makes it easier to see why behavior changed, test the repair, review the risk, and revert it cleanly if the diagnosis is wrong.

Check a wider area one step at a time

1 / Exact case

Does the reported or recreated case now behave as expected?

2 / Nearby cases

Do closely related success and failure paths still behave correctly?

3 / Package tests

Do the component’s ordinary tests still pass?

4 / Running system

Do production or staging metrics support the wider claim? What is still unknown?

05

Say what remains unknown

A useful handoff separates impact, cause, repair, and verification. It tells the next responder what is known without hiding what has not been checked.

Three-minute structure / short but complete

Explain what happened and why; do not merely list commands.

Incident handoff template
Impact:
  What users or systems experienced, over what scope and time.

Confirmed scope:
  Who, where, and when was affected, and what evidence supports that statement.

Key evidence:
  The observations that separated the leading possible causes.

First wrong step:
  The earliest place in code we own where behavior became wrong.

Repair:
  The exact behavior change and why it fixes the problem.

Verification:
  Focused reproduction, neighboring cases, and broader checks.

Still unknown:
  What has not been checked or belongs to another component.

Preventive follow-up:
  One test, release check, metric, or log improvement.

Avoid

  • “Fixed” without naming the confirmed scope.
  • A command transcript with no explanation of what each result established.
  • Mixing up the visible symptom, the defect in this code, and the wider incident.
  • Claiming another component behaved a certain way without evidence.
  • A prevention backlog disguised as part of the emergency repair.
06

Write for the next incident

The repair closes one defect. The lesson lasts only when the codebase makes a similar incident easier to understand next time.

Prevention / keep what we learned

Put each production lesson somewhere it will be used.

Focused test

Record the expected behavior in the smallest part of the code that owns it. Include important error cases and, when relevant, more than one implementation.

Release check

Run the test where risky changes enter: a new adapter, migration, small canary rollout, or compatibility test.

Metrics and logs

Add signals that separate the main possible causes. Use a few useful labels rather than a flood of messages.

API comment

Put responsibility for starting and stopping work, cancellation, and unusual behavior beside the API so responders do not need to rely on team memory.

Incident note

Record the surprising cause and the shortest useful path to finding it, without turning ordinary code comments into a postmortem.

The expanded style guide matters during incident response for practical reasons: clear names are easier to search, small interfaces reduce what must be read, wrapped errors keep their cause, context shows cancellation, and stable tests make repairs easier to check.

07

Release and deploy safely

A repair is not finished when it compiles. We also need a controlled way to put it into service, see unexpected changes quickly, and return to a known-good state.

Release engineering / make safe behavior routine

Deploying code and activating behavior are different operations.

Software has to change. The practical aim is not to avoid releases, but to make ordinary releases small enough to observe and easy enough to stop. Sarah Murphy’s Principles of Release Engineering describes this in terms of preserving a known-good state, rolling out changes in stages, reducing the time and attention required to ship, and treating unexpected production changes as bugs.

DeployPut the new version in place.

The binary can contain both the established and new behavior while production continues to use the established path.

ActivateChoose who receives the change.

A feature flag, canary, region, or traffic rule lets the team increase exposure deliberately.

ObserveKnow what must remain healthy.

Compare errors, latency, resource use, and the important user action against the state before activation.

ReverseDecide how to get back first.

Turning off a flag or routing traffic back is safer than inventing a repair while the impact is growing.

Keep the established path available during rollout

A simplified application gate
type Searcher interface {
    Find(context.Context, string) ([]Result, error)
}

type Rollout interface {
    Enabled(feature, subject string) bool
}

type SearchHandler struct {
    established Searcher
    candidate   Searcher
    rollout     Rollout
}

func (h *SearchHandler) searcherFor(accountID string) Searcher {
    if h.rollout.Enabled("search-v2", accountID) {
        return h.candidate
    }
    return h.established
}

Shipping this binary does not require enabling search-v2. Activation can begin with a small group, stop without another build, and retain the established path until the candidate has proved safe.

Production example / Grafana Cloud, February 2025

A narrow test passed; the full deployment failed.

A TLS-policy override remained in place after configuration reconciliation in development. A complete redeployment was not tested. When the merge-policy change reached every environment together, it also changed Kubernetes Services from LoadBalancer to ClusterIP, causing Kubernetes to destroy the load balancers.

Summary of Grafana Labs’ public incident report
Test the whole change

Confirm the result after creating or replacing the managed resource, not only after updating one field on a resource that already exists.

Enforce the first wave

Make development the default first destination. Reaching staging or production together should require an explicit exception.

Hold and compare

After each wave, check the expected change and unrelated critical behavior. A healthy process is not enough if a load balancer or another external resource disappeared.

Stop on an unexpected change

Rollback or deactivate first when that is safe. Investigate after impact has stopped growing and evidence has been preserved.

Plan stored-state changes separately

A binary can often be rolled back; a schema, membership record, or destructive external action may not be. Such changes need their own staged compatibility and recovery plan.

Source and limit: Grafana Labs reports that the incident lasted about 150 minutes and affected roughly 25% of its services. Its public report explains the testing gap, bypassed deployment waves, rollback, and new automated checks, but does not link the implementation PR. It supports the release lesson here; it is not presented as a Go code case. Read “How we responded to a 2+ hour partial outage in Grafana Cloud.”

Production example / Argo CD, 2024–2025

A preview must not perform the destructive part of an operation.

Jobs marked Force=true,Replace=true were created during Argo CD’s dry-run phase and then created again during their sync waves. In another report, the preview-created Job acquired a finalizer—a marker that prevents deletion until cleanup finishes. Replacement waited for that deletion, and the application remained in Progressing.

Summary of public Argo CD and GitOps Engine reports

The word “dry run” describes an intended result, not proof that every function called underneath is harmless. Kubernetes force-replace can delete and recreate a resource. Passing the same force value to preview and apply therefore allowed the preview path to change the cluster.

One option set is reused for two different jobs
func replace(mode Mode, force bool) error {
    options := ReplaceOptions{
        DryRun: mode == Preview,
        Force:  force,
    }
    return options.Run()
}
Preview cannot request destructive replacement
func replace(mode Mode, force bool) error {
    options := ReplaceOptions{
        DryRun: mode == Preview,
        Force:  force && mode == Apply,
    }
    if err := options.Validate(); err != nil {
        return fmt.Errorf("validate replace: %w", err)
    }
    return options.Run()
}

Teaching inference: preview, validation, planning, and apply paths need tests that assert which external calls occur—not merely the returned status. Include resources with finalizers and ordered sync waves. The repairing PR changed the production path but added no direct test coverage for its new lines, so it is evidence of the repair, not a complete testing model to copy.

Source trail: read GitOps Engine issue #623, Argo CD issue #23570, and repair PR #633. The Go code above is an original reduction of the option-handling problem, not Argo source.

08

Wheels of Misfortune

Nine short investigations turn recent production write-ups and open-source change records into new Go examples. They practice reading reports and choosing useful evidence without repeating the bugs in go-crucible’s numbered exercises.

How to use sources

Common bug patterns give us leads, not proof.

A short list of goroutine leak patterns can help at the start of an investigation. It gives a responder names for blocked sends, missing cancellation, and untracked work. It does not show which one, if any, caused this incident.

Check even familiar examples against the Go specification. A receive from a closed channel is ready immediately; without the two-value receive it can create a hot loop rather than a blocked goroutine. A channel buffer can delay a blocked send without deciding who must receive it. A WaitGroup can wait for completion, but cannot cancel the work.

Source trail

Follow the work from report to test.

Original report → design or Kubernetes Enhancement Proposal (KEP) → implementation PR → compatibility tests → benchmark. Each source answers a different question. If they disagree, investigate the difference.

How to read the debriefs: cause, repair, and reported-result statements summarize the linked sources. Labels beginning with “Suggested” and the broader prevention or release lessons are teaching inferences unless the text explicitly attributes them to a report, test, or pull request.

Wheel of Misfortune A / The Quiet Batch

Low request rate, disappearing ports.

Go fan-outIntermediateSource: April 202620 minutes

One data-center site is intermittently failing cache operations with “address already in use.” Request rate is ordinary, cache latency rose across unrelated object types, and a recent internal client sends fewer than three requests per second. The status update blames packet loss between the cloud provider and the site.

Teaching report — facts adapted, names and system simplified

Before opening code

Write two possible causes.
  • A network path is dropping or delaying cache traffic.
  • A client workload is exhausting a local resource shared by all cache calls.
  • The cache service itself is rejecting one object type.

Choose one first packet

Which result most sharply separates them?
  1. Total requests per second by endpoint.
  2. Batch-size distribution and in-flight cache dials by caller.
  3. All cache error logs from the affected site.
  4. A traceroute from the affected site.

Simplified Go example — not the production source

Object loader
func LoadObjects(
    ctx context.Context,
    keys []string,
) ([]*Object, error) {
    objects := make([]*Object, len(keys))
    group, ctx := errgroup.WithContext(ctx)

    for index, key := range keys {
        group.Go(func() error {
            object, err := loadOne(ctx, key)
            if err != nil {
                return fmt.Errorf("load %q: %w", key, err)
            }
            objects[index] = object
            return nil
        })
    }

    if err := group.Wait(); err != nil {
        return nil, err
    }
    return objects, nil
}
Open debrief — cause, repair, and prevention

Cause: request count hid the size of each request. A low-rate client could send a batch large enough to create thousands of cache operations at once. Those connections consumed ephemeral ports. Because all cache calls shared those ports, unrelated paths also failed. Logging every failure then made the overloaded process do even more work.

Bound work before launching it
group, ctx := errgroup.WithContext(ctx)
group.SetLimit(50)

for index, key := range keys {
    group.Go(func() error {
        object, err := loadOne(ctx, key)
        if err != nil {
            return fmt.Errorf("load %q: %w", key, err)
        }
        objects[index] = object
        return nil
    })
}

Suggested verification: exercise the largest supported batch; assert the concurrency ceiling; cancel while submissions are waiting for capacity; confirm each newly admitted task observes the canceled context before starting dependency work; and verify that the same logical results are returned. SetLimit bounds active goroutines, but it does not make the capacity wait inside Group.Go cancellation-aware. If submission itself must stop immediately, use a worker pool or an explicit context-aware admission step.

Teaching recommendation: measure batch size and in-flight work per caller, not only requests per second. Rate-limit repetitive error reporting so the failure path cannot dominate the process.

Basis: Jim’s Pckt, “April 2026 Outage Post-Mortem,” a first-person production account with Go code showing a missing errgroup limit, unusually large batches, port exhaustion, and a logging-driven death spiral. This exercise changes the domain and rewrites the code. Read the production account and the official errgroup.SetLimit documentation.

Wheel of Misfortune B / The Healthy Certificate

Green probes, red browsers.

Probe the user pathsBeginnerSource: March 202415 minutes

Users report an expired certificate on the documentation site roughly 90 days after a hosting migration. Certificate-expiry monitoring remains green. The site publishes both A and AAAA records; IPv6 passes through a team-managed proxy, while IPv4 reaches the hosting provider directly.

Teaching report — architecture adapted from a public outage

Classify the evidence

What does “the probe passed” establish?

It establishes that one resolved address and one handshake returned a valid certificate. It does not yet establish that every user-visible network path terminates at the same certificate.

Ask what changes the path

What can send the probe to a different server?

Address family, resolver location, CDN or proxy routing, SNI, region, and protocol can all make two checks of the “same hostname” observe different infrastructure.

Simplified Go probe

A check with an unstated path
func certificateExpiry(
    ctx context.Context,
    hostname string,
) (time.Time, error) {
    dialer := &tls.Dialer{
        Config: &tls.Config{ServerName: hostname},
    }

    conn, err := dialer.DialContext(ctx, "tcp", hostname+":443")
    if err != nil {
        return time.Time{}, fmt.Errorf("dial %s: %w", hostname, err)
    }
    defer conn.Close()

    state := conn.(*tls.Conn).ConnectionState()
    return state.PeerCertificates[0].NotAfter, nil
}
Open debrief — cause, repair, and prevention

Cause: the check saw a real certificate, but only on the path chosen by normal name resolution. In the source incident, the probes checked IPv6 through a proxy with a healthy certificate. IPv4 users reached the hosting provider’s certificate, which had failed to renew.

Make the network path explicit
type CertificateTarget struct {
    Name       string
    Network    string // tcp4 or tcp6
    Address    string
    ServerName string
}

func probeCertificate(
    ctx context.Context,
    target CertificateTarget,
) (time.Time, error) {
    dialer := &net.Dialer{}
    raw, err := dialer.DialContext(ctx, target.Network, target.Address)
    if err != nil {
        return time.Time{}, fmt.Errorf("dial %s: %w", target.Name, err)
    }

    conn := tls.Client(raw, &tls.Config{ServerName: target.ServerName})
    defer conn.Close()
    if err := conn.HandshakeContext(ctx); err != nil {
        return time.Time{}, fmt.Errorf("handshake %s: %w", target.Name, err)
    }
    return conn.ConnectionState().PeerCertificates[0].NotAfter, nil
}

Suggested verification: configure explicit IPv4 and IPv6 targets, label their results separately, and test that one failing path cannot be hidden by another passing path.

Preventive question: does each automated check follow a real user path, or merely prove that some route works?

Basis: Tailscale, “About the Tailscale.com outage on March 7, 2024.” Its certificate probes covered IPv6 only and therefore observed a different certificate path from affected IPv4 users. The Go prober above is an original teaching implementation. https://tailscale.com/blog/tls-outage-20240307

Wheel of Misfortune C / The Trusted Feature File

A generated input crosses the fleet.

Configuration activationAdvancedSource: November 202520 minutes

Core proxies begin returning 5xx responses across the fleet. Traffic volume is elevated, so the first theory is a large DDoS attack. Minutes earlier, a database-permission change altered the rows visible to an internal feature-file generator. The resulting file is roughly twice its usual size.

Teaching report — facts adapted from Cloudflare’s postmortem

Possible causes

Attack load or shared configuration file?
  • External traffic exceeds proxy capacity.
  • A shared configuration file makes normal traffic fail.
  • A downstream dependency fails independently.

A useful comparison

Compare when the file arrived with when failures began.

Ask whether crashes follow traffic rate, receipt of one file version, or both. Inspect the first panic or load error before repeated failures fill the logs.

Simplified Go file loader

Generated does not mean safe
const maxFeatures = 200

func (m *Model) Activate(raw []byte) {
    var file FeatureFile
    if err := json.Unmarshal(raw, &file); err != nil {
        panic(err)
    }
    if len(file.Features) > maxFeatures {
        panic("feature capacity exceeded")
    }

    compiled, err := compileFeatures(file.Features)
    if err != nil {
        panic(err)
    }
    m.active.Store(compiled)
}
Open debrief — cause, repair, and prevention

Cause: a permissions change made a database query return more rows than intended. The generated file exceeded the reader’s fixed limit. Loading the file turned that expected error into a panic, and sending the same file across the fleet made every proxy vulnerable to the same failure.

Validate before replacing known-good state
func (m *Model) Activate(raw []byte) error {
    var file FeatureFile
    if err := json.Unmarshal(raw, &file); err != nil {
        return fmt.Errorf("decode feature file: %w", err)
    }
    if len(file.Features) > maxFeatures {
        return fmt.Errorf(
            "feature file has %d entries, maximum is %d",
            len(file.Features),
            maxFeatures,
        )
    }

    compiled, err := compileFeatures(file.Features)
    if err != nil {
        return fmt.Errorf("compile feature file: %w", err)
    }
    m.active.Store(compiled)
    return nil
}

Suggested verification: malformed, oversized, duplicate, and otherwise invalid files must leave the last-known-good state active. Test the file writer and reader separately, then test a staged rollout and rollback.

Teaching recommendation: treat generated configuration like user input; send it to a small canary group before the whole fleet; retain a kill switch; and ensure error reporting cannot itself exhaust memory or CPU.

Basis: Cloudflare, “Cloudflare outage on November 18, 2025.” The postmortem documents an internal query returning duplicate metadata after a permission change, a feature file exceeding a fixed limit of 200 features, an unhandled error that panicked, and the same bad file being sent across the fleet. The Go code above is an original example of the same kind of failure, not Cloudflare source. https://blog.cloudflare.com/18-november-2025-outage/

Wheel of Misfortune D / The Sixteenth Informer

A few allowed requests can still use all the memory.

Buffering a whole responseAdvancedSources: 2024–202525 minutes

After a short control-plane network interruption, controllers reconnect and issue LIST requests. API server replicas are terminated after running out of memory, often called being OOM-killed. The server handles no more requests than its configured limit, and small-cluster tests pass. A reproduction with 400 one-megabyte objects fails when the sixteenth informer—a controller-side component that watches resources and maintains a local cache—joins.

Synthetic incident report — adapted from Kubernetes scalability demonstrations, not presented as a historical outage

Do not stop at “retry storm”

What can still grow too large?
  • The number of LIST requests handled at once.
  • The bytes held while each response is still being sent.
  • The objects returned by storage.
  • The client’s reconnection delay.

Choose the next evidence

Measure request count and response size separately.
  1. Graph heap growth by response bytes and concurrent LIST calls.
  2. Capture an allocation profile during one large response.
  3. Compare time to first byte with total encoding time.
  4. Repeat with the same concurrency and smaller objects.

Simplified Go encoder

One write first builds the whole response
type ListResponse[T any] struct {
    Items []T `json:"items"`
}

func writeList[T any](
    w http.ResponseWriter,
    response ListResponse[T],
) error {
    encoded, err := json.Marshal(response)
    if err != nil {
        return fmt.Errorf("encode list: %w", err)
    }
    if _, err := w.Write(encoded); err != nil {
        return fmt.Errorf("write list: %w", err)
    }
    return nil
}
Open debrief — cause, repair, and source trail

Cause: limiting the number of requests did not limit the memory used by each request. The encoder first built the whole response in one byte slice. Peak encoding memory therefore grew with requests at once × response size. A slow connection kept each large allocation alive longer. Reused buffers could also keep the heap large after the request ended.

Write one item at a time
func writeItems[T any](w io.Writer, items []T) error {
    if _, err := io.WriteString(w, `{"items":[`); err != nil {
        return fmt.Errorf("write list prefix: %w", err)
    }
    for index := range items {
        if index > 0 {
            if _, err := io.WriteString(w, ","); err != nil {
                return fmt.Errorf("write item separator: %w", err)
            }
        }
        encoded, err := json.Marshal(items[index])
        if err != nil {
            return fmt.Errorf("encode item %d: %w", index, err)
        }
        if _, err := w.Write(encoded); err != nil {
            return fmt.Errorf("write item %d: %w", index, err)
        }
    }
    if _, err := io.WriteString(w, `]}`); err != nil {
        return fmt.Errorf("write list suffix: %w", err)
    }
    return nil
}

Do not mistake the sketch for the Kubernetes patch. The real implementation had to preserve JSON and Protocol Buffer output byte for byte, validate Go struct tags, handle gzip chunking and repeated writer calls, cover built-in and custom list types, and retain client compatibility. Those constraints are visible in the linked proposal, pull requests, and tests.

Suggested verification: compare old and new bytes across all supported list types; measure memory as both item size and number of items grow; test slow and failed writers; exercise compression; and confirm that partial writes do not look like complete responses.

Result in the Kubernetes benchmark: ten one-gigabyte LIST responses running at once fell from roughly 70–80 GB of memory to about 3 GB. The encoder no longer needs another full-sized copy of the list. Most of its extra memory is used for the item being written and the network buffers.

Source trail: Kubernetes first published a large-scale demonstration of API server memory pressure, then documented the v1.33 streaming encoder and benchmark. Kubernetes Enhancement Proposal (KEP) 5116 links the implementation, compatibility tests, checks for incorrect struct tags, compression work, and benchmarks. Read the 2024 scalability demonstration, 2025 streaming LIST article, KEP 5116, JSON encoder PR #129334, and Protocol Buffer encoder PR #129407.

Wheel of Misfortune E / The Queue Says It Is Keeping Up

An hour behind, with no reason to add workers.

Measurement under loadAdvancedSource: October 202525 minutes

After an upgrade, several remote-forwarding installations fall more than an hour behind. The affected sites have slower network links, but CPU remains below 20%, memory below 25%, and the queue uses only three or four workers despite a configured maximum of 75. Rolling back clears the lag. Reapplying the upgrade reproduces it.

Teaching report — facts adapted from a public Prometheus regression

Possible causes

Do not equate spare CPU with a healthy pipeline.
  • The remote receiver cannot accept more data.
  • The network is too slow for any worker count to help.
  • The queue’s scaling calculation understates incoming work.
  • Workers are available but unable to make progress.

Choose the next evidence

Compare the pipeline at more than one boundary.
  1. Count records committed to local storage.
  2. Count records admitted to the forwarding queue.
  3. Count records successfully sent.
  4. Graph queue capacity, desired workers, and actual workers together.

Simplified Go example — not Prometheus source

The queue’s view of incoming work
type Queue struct {
    pending  chan Sample
    observed atomic.Uint64
}

func (q *Queue) Enqueue(
    ctx context.Context,
    sample Sample,
) error {
    select {
    case q.pending <- sample:
        q.observed.Add(1)
        return nil
    case <-ctx.Done():
        return context.Cause(ctx)
    }
}
Open debrief — cause, repair, and release lesson

Cause: the source change moved the input measurement closer to the forwarding queues. Work contributed to the measured input rate only after it entered a queue. When the queues filled, producers blocked before the counter advanced. The scaler could therefore observe an input rate no greater than the output rate, even while unsent data accumulated elsewhere. It saw no reason to add workers.

Measure committed input in the write-ahead log (WAL), before the constrained queue
type Receiver struct {
    wal      *WAL
    received atomic.Uint64
}

func (r *Receiver) Commit(batch []Sample) error {
    if err := r.wal.Append(batch); err != nil {
        return fmt.Errorf("append input batch: %w", err)
    }
    r.received.Add(uint64(len(batch)))
    return nil
}

Repair: Prometheus reverted the queue scaling behavior to the known-good 3.6 logic. The original developers continued to consider how to improve the design, but did not hold the urgent production repair for that redesign.

Reported verification: the repair PR added a higher-level test that constrains forwarding, creates enough input to require more shards, and checks that the system scales up. The test failed on the broken branch and passed with the revert.

Reported release evidence: the reporter rolled back, observed recovery, reapplied the upgrade, and observed the same regression. That sequence did not by itself identify the defective line, but it sharply limited the search and protected the affected installations.

Source trail: the public Prometheus report includes versions, resource use, queue settings, production graphs, two successful rollbacks, and reports from more than one environment. The discussion then narrows the problem to where the scaling calculation measures input. Read issue #17384, the diagnostic PR #17407, and the release-3.7 revert and regression test in PR #17412.

Wheel of Misfortune F / The Members That Came Back

The first upgraded node remembers a different cluster.

Stored-state migrationAdvancedSource: November–December 202530 minutes

The first node in a five-node cluster is upgraded from version 3.5.25 to 3.6.6. It reports old members that were removed years ago. The old and current members have different IDs but duplicate names and peer addresses. A query to an unchanged 3.5 node still shows the expected five members, and attempts to reproduce the problem with a newly created cluster fail.

Teaching report — facts adapted from an etcd production bug report

Classify the observations

Which facts depend on the node or its history?
  • The duplicate IDs appear after one node changes version.
  • Different-version nodes report different membership lists.
  • The duplicate addresses belonged to real former members.
  • A clean cluster has no history of removals or recovery.

Choose the next evidence

Compare what each version reads, not only what its API returns.
  1. Record the membership view from every node before changing another one.
  2. Inspect both persisted membership representations on the affected node.
  3. Reconstruct member additions, removals, restores, and forced recovery operations.
  4. Check whether the upgrade changes which stored copy each version trusts.

Simplified Go model — not etcd source

Two releases choose different stored membership
type Release int

const (
    Release35 Release = iota
    Release36
)

func LoadMembers(
    release Release,
    stores MembershipStores,
) ([]Member, error) {
    if release == Release35 {
        return stores.LoadLegacy()
    }
    return stores.LoadCurrent()
}
Open debrief — cause, repair, and safe upgrade path

Cause: etcd 3.5 trusted its older membership representation, called v2store, even though membership was also present in a newer representation called v3store. etcd 3.6 switched to the v3store copy. Some long-running clusters had accumulated inconsistencies between the two through earlier member removal or recovery paths. Version 3.5 continued to operate from the expected records; version 3.6 exposed the stale ones.

Repair the next source before switching to it
func PrepareUpgrade(stores MembershipStores) error {
    members, err := stores.LoadLegacy()
    if err != nil {
        return fmt.Errorf("load 3.5 membership: %w", err)
    }
    if err := stores.ReplaceCurrent(members); err != nil {
        return fmt.Errorf("repair current membership: %w", err)
    }
    if err := stores.Sync(); err != nil {
        return fmt.Errorf("persist repaired membership: %w", err)
    }
    return nil
}

Repair: etcd 3.5.26 added an automatic synchronization from the membership source used by 3.5 to the source that 3.6 would use. The safe sequence is therefore 3.5.26 or later, wait for and confirm cluster health, then 3.6.

An earlier repair missed a different path: etcd 3.5.20 repaired learner promotion records, but a rolling replacement could still copy an older member’s incorrect snapshot into a newer member. The cluster continued working while 3.5 trusted v2store; the error appeared later when 3.6 trusted v3store. Version 3.5.24 corrected membership while applying such a snapshot. The first fix was not pointless or wrong—it covered the path that had been reproduced—but the real upgrade sequence found another way for old state to survive.

Why the clean reproduction failed: the inconsistent state depended on the real cluster’s history. A fresh cluster exercised the new code without recreating old snapshots, removal behavior, forced recovery, crash timing, or other paths that might have left the stores different.

Suggested verification: start with deliberately inconsistent stored membership, run the repair release, restart every member, and then upgrade one member at a time. Confirm both stored copies and the API view after every step. Keep fixtures for several known histories, but do not claim that the known histories cover every possible cause.

Teaching inference: rollback is more complicated once a release changes durable state. The upgrade design must say which versions can run together, when the new version begins trusting the new copy, how old state is repaired, and what operators should check before proceeding.

Source trail: the original report contains the five-node production history, exact versions, per-node output, duplicate IDs and addresses, logs, and failed attempts to reproduce from scratch. The etcd project’s follow-ups explain the two membership stores, several known ways they could diverge, repairs in successive 3.5 releases, and the required upgrade order. Read issue #20967, “Avoiding Zombie Cluster Members When Upgrading to etcd v3.6”, repair PR #20995, and the etcd 3.5.26 release. For the earlier rolling-replacement path, read the official October 2025 follow-up, issue #20793, and repair PR #20797.

Wheel of Misfortune G / The Restart That Waited for Itself

Only nodes receiving DNS traffic fail to restart.

Startup deadlockIntermediateSource: September–November 202425 minutes

After an upgrade to Cilium 1.16, one agent takes three minutes to start, exits, and then succeeds on its second attempt. The affected node has a workload selected by an application-layer (L7) DNS policy. If that workload is idle, startup often succeeds; if it is resolving names, startup fails. The same failure is reported with and without Envoy or Container Network Interface (CNI) chaining, and it remains after removing kube-proxy.

Teaching report — facts adapted from Cilium issue #35080

Separate signal from coincidence

Which differences track the failure?
  • The same six Kubernetes resources finish their initial synchronization.
  • A policy resource waits until the three-minute startup timeout.
  • Active DNS traffic changes whether the failure appears.
  • A race-detector warning in iptables disappears after locking, but the startup failure remains.

Choose the next evidence

Capture what is waiting, then trace who holds it.
  1. Take goroutine stacks before the startup timeout.
  2. Identify locks held by endpoint restoration and policy synchronization.
  3. Trace callbacks that DNS traffic can invoke before startup completes.
  4. Compare the endpoint-restoration path with first-time endpoint creation.

Simplified Go model — not Cilium source

Restoration enables a callback before the endpoint is ready
func parseRestoredEndpoint(data []byte) (*Endpoint, error) {
    endpoint, err := decodeEndpoint(data)
    if err != nil {
        return nil, fmt.Errorf("decode endpoint: %w", err)
    }
    endpoint.initDNSHistoryTrigger()
    return endpoint, nil
}

func (e *Endpoint) observeDNS(answer DNSAnswer) {
    e.history.Add(answer)
    e.dnsHistoryTrigger.Trigger()
}
Open debrief — cause, repair, and misleading evidence

Cause: restored endpoints started a DNS-history trigger while the agent was still starting. DNS traffic could fire the trigger and request endpoint regeneration. Regeneration needed startup work to finish, while startup was waiting with the endpoint locked. Each side waited for progress that the other side prevented.

Initialize the trigger during the first regeneration
func parseRestoredEndpoint(data []byte) (*Endpoint, error) {
    endpoint, err := decodeEndpoint(data)
    if err != nil {
        return nil, fmt.Errorf("decode endpoint: %w", err)
    }
    return endpoint, nil
}

func (e *Endpoint) regenerate(ctx context.Context) error {
    e.initDNSHistoryTrigger()
    return e.writeHeader(ctx)
}

Repair: Cilium removed the unnecessary trigger initialization from endpoint parsing. The normal first regeneration already initialized it at a safe point. The upstream production change deleted two lines and was backported to Cilium 1.16.4.

Why the race warning was not the cause: it was a real defect worth repairing, but adding a lock made the warning disappear without changing the reported failure. Evidence can uncover more than one bug; a candidate cause must also change the symptom or explain the complete sequence.

Suggested verification: restore an endpoint selected by an L7 DNS policy, generate DNS traffic throughout agent startup, and assert that startup completes without waiting for the global timeout. Repeat enough times to cover the timing window and confirm that DNS history still works after regeneration.

Teaching inference: restart tests need realistic live traffic and restored state. A test that creates only new endpoints cannot cover a defect confined to the restoration path.

Source trail: the community report records affected and unaffected versions, controlled comparisons, stack traces, a real but unrelated race, and confirmation from several environments. Read Cilium issue #35080, repair PR #35890, and the Cilium 1.16.4 release notes.

Wheel of Misfortune H / The Replicas That Agreed

Every copy can agree that live data is gone.

Range split raceAdvancedSource: February 202635 minutes

A CockroachDB cluster reports no ordinary replica inconsistency, but a recently written row is missing. The table has long runs of deleted sequential keys and occasionally receives corrections in old key ranges. Near the missing write, multi-version concurrency control (MVCC) garbage collection and a range split ran at nearly the same time.

Teaching report — reconstructed from CockroachDB Technical Advisory 162085

CockroachDB divides its ordered keys into ranges and keeps several copies of each range. MVCC retains old versions of a key so transactions can read a consistent point in time; garbage collection later removes versions that are no longer needed. For a long span of obsolete keys, a range tombstone can delete the span more efficiently than deleting keys one at a time. A latch is a short-lived internal lock that prevents conflicting operations on the same keys.

Do not equate agreement with correctness

What operation could reach every copy?
  • Garbage collection found at least 2,000 consecutive obsolete versions.
  • The range split inside that span while the request was being prepared.
  • A new write landed on the new right-hand range before clearing finished.
  • The clear operation was created by the old left-hand range.

Choose the next evidence

Compare the advertised span with the actual deletion.
  1. Build a timeline of GC, the split, and the new write.
  2. Record the range bounds used to route and latch the request.
  3. Record every key span the request will actually clear.
  4. Check whether the two spans are validated together after the split.

Simplified Go model — not CockroachDB source

Coordination follows the header; deletion follows another span
type ClearRequest struct {
    Header Span
    Clear  Span
}

func (r *Replica) apply(req ClearRequest) error {
    release := r.latches.Lock(req.Header)
    defer release()

    if !r.bounds().Contains(req.Header) {
        return ErrRangeChanged
    }
    return r.store.Clear(req.Clear)
}
Open debrief — cause, repair, and why checks could miss it

Cause: GC identified a clearable span before a split. After the split, the request header described the left-hand range, but the ClearRange operation could still extend into the new right-hand range. Latches protected only the advertised left-hand work. A right-hand write could therefore succeed and then be removed when the old clear operation reached the same underlying storage.

Validate and protect the keys that will actually be cleared
func (r *Replica) apply(req ClearRequest) error {
    release := r.latches.Lock(req.Clear)
    defer release()

    current := r.bounds()
    if !current.Contains(req.Clear) {
        return ErrRangeChanged
    }
    return r.store.Clear(req.Clear)
}

Repair: CockroachDB added checks for GC keys that straddle the request header and tightened how the request span is constructed and validated. The exact production repair is more defensive than the sketch above; the important rule is that routing, latching, validation, and storage must describe the same keys.

Why replicas could agree: after a split, the left- and right-hand ranges can still share the same storage on a node. Applying the same range tombstone on the left-hand replicas can therefore delete the right-hand key on every replica. Agreement proves that the same operation ran; it does not prove that the operation was valid.

Detection: a secondary index may retain evidence that the primary row disappeared, and some timing variants can make replicas diverge. Neither is guaranteed. The advisory therefore recommends patched releases rather than relying on detection alone.

Suggested verification: reproduce all three required events—an eligible obsolete span, a split inside it, and a new write on the right before clearing completes. Assert that an old request is rejected or rebuilt and that the new write survives.

Source trail: the CockroachDB advisory gives the required timing, affected versions, mitigations, detection limits, and technical sequence. The issue and PR expose the production discussion, tests, backports, and follow-up hardening. Read Technical Advisory 162085, issue #162085, and repair PR #162271.

Wheel of Misfortune I / The Index Built from Missing Columns

An optimization that is safe for ordinary updates corrupts a backfill.

Schema change under writesAdvancedSource: March–April 202630 minutes

After a partial index is created online, queries forced through that index disagree with the primary index. Some rows are missing, some contain unexpected NULL values, and some no longer satisfy the index predicate. The table uses multiple column families and continued receiving updates while the index was backfilled.

Teaching report — reconstructed from CockroachDB Technical Advisory 166122

A partial index contains only rows that match a condition, such as status = 'active'. A backfill creates index entries for rows that existed before the index while ordinary writes continue. CockroachDB column families can store different groups of columns separately, so updating one family does not necessarily fetch values from another.

Identify the special execution mode

What is different during a backfill?
  • The new index is incomplete and is still being assembled.
  • Concurrent updates must also be written to a temporary index.
  • The merger needs a complete view of each changed row.
  • Columns in another family may not be fetched automatically.

Choose the next evidence

Read the same rows through independent paths.
  1. Compare the partial index with the primary index in both directions.
  2. Record which columns the update plan fetched.
  3. Record whether the partial-index write was simplified away.
  4. Repeat with one column family and then several.

Simplified Go optimizer — not CockroachDB source

Ordinary-update rules are also applied to an index being built
func optimizeUpdate(plan *UpdatePlan) {
    if plan.indexColumnsUnchanged() {
        plan.dropUnneededFetchColumns()
        plan.skipPartialIndexWrite()
    }
}
Open debrief — cause, repair, and evidence

Cause: two optimizer rules were correct for an established index. If an update did not change index columns, the plan could avoid fetching them and avoid writing the unchanged index entry. During a backfill, however, the temporary index still needed the complete row and a write for every concurrent update. With several column families, omitted columns arrived as NULL; skipped writes produced missing or phantom rows.

Do not apply ordinary-update shortcuts to an index being built
func optimizeUpdate(plan *UpdatePlan) {
    if plan.IndexIsBeingBuilt() {
        plan.fetchAllIndexColumns()
        plan.keepPartialIndexWrite()
        return
    }
    if plan.indexColumnsUnchanged() {
        plan.dropUnneededFetchColumns()
        plan.skipPartialIndexWrite()
    }
}

Repair: the optimizer now keeps required columns and predicate evaluation for indexes being built. The production PR changed the catalog and normalization rules and added a larger regression test covering concurrent updates during the backfill.

Why common tests passed: single-column-family tables fetched the whole family when any column changed, accidentally supplying the omitted values. Tests also need concurrent updates; a backfill over an idle table does not exercise the temporary-index merge path.

Detection: compare the results in both directions: primary index minus partial index, then partial index minus primary index. The first comparison finds rows missing from the partial index; the second finds extra or incorrect partial-index rows.

Teaching inference: an optimization is valid only under its stated conditions. When a mode such as migration, recovery, preview, or backfill changes what downstream code requires, make that mode visible in the plan and test it explicitly.

Source trail: the public advisory states the required conditions, affected versions, repair releases, detection queries, and three forms of corruption. The issue and production PR explain the two optimizer rules and add the regression test. Read Technical Advisory 166122, issue #166122, and repair PR #166123.
