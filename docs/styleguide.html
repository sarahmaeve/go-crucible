Important

In this guide, a contract is simply behavior that callers are allowed to rely on: accepted inputs, returned values and errors, which code is responsible for each resource, and when work ends.

01

Judgment & scope

Style is not cosmetic polish. It helps code show what must remain true, which part owns each task, and how failures are returned or reported.

Protocol / interpret the language

Not every sentence has the same force.

A compiler constraint, a repository convention, and a useful testing technique are different kinds of advice. Treating all three as “must” creates churn and can make code worse. Use these five levels when applying the guide:

01Requirement

Enforced by Go, tooling, or documented behavior that callers rely on.

02Strong convention

The normal choice; depart when local facts make another choice safer or clearer.

03Project convention

A consistency choice for go-crucible, not a universal law.

04Technique

A tool for a named problem, not a dependency to add by default.

05Teaching exception

Starter code may contain the defect it teaches without endorsing that defect.

The label before each rule group states its dominant level. When a group combines levels, the source trail distinguishes documented Go or package behavior from project choices and techniques for particular problems.

How to choose / five priorities

When advice conflicts, clarity wins first.

Readable Go makes its purpose and reasons obvious, uses the simplest tool that works, removes distractions, remains safe to change, and fits the surrounding code. That order matters. Consistency is valuable, but it does not rescue a locally confusing pattern.

  1. Clarity: can a reader explain what the code promises and why?
  2. Simplicity: is there a smaller solution with the same behavior and performance?
  3. Concision: can any code or explanation be removed without losing useful information?
  4. Maintainability: will a plausible change fail visibly rather than silently?
  5. Consistency: does the choice match the nearest healthy pattern?

Review prompt

Ask “what could a reasonable maintainer misunderstand?” before asking “which rule number applies?”

02

Shape of the code

Formatting is automated. Structure is still a human decision: make control flow visible, reduce nesting, and let complexity announce itself.

Strong conventions / Rules 01 · 08–15 · 30 · 37–38

Let tools settle whitespace; arrange code to show meaning.

All hand-written Go must match gofmt. Beyond that, Go has no official maximum line length. If a line feels too long, first ask whether the operation itself has too many responsibilities or arguments. Break a line where its meaning changes, and only when the result is easier to read.

  • Handle errors and edge cases first so the successful path stays flat.
  • Use a switch when cases describe the same subject.
  • If complexity is necessary, name it, explain why it exists, test it, and benchmark it when performance is the reason.
  • Name fields in struct literals for types from another package. Positional literals couple callers to the type’s field order and complete field set.
  • Group imports as standard library, other packages, protocol buffers, then side effects. Avoid dot imports.

Match nearby clear code

When two choices are equally clear, match the file, then the package, then the project. Do not repeat a confusing pattern merely because it already exists.

Nested / hard to scan
result, err := load(ctx, id)
if err != nil {
    return err
} else {
    if result.Enabled {
        publish(result)
    }
}
return nil
Flat / intent visible
result, err := load(ctx, id)
if err != nil {
    return fmt.Errorf("load %q: %w", id, err)
}
if !result.Enabled {
    return nil
}
publish(result)
return nil

Variable declarations communicate starting state

Use := when a value is known and var when the useful zero value—the default Go assigns to an uninitialized variable—is the point. This is a readability guideline; it does not change what the declaration means.

attempts := 3        // the value matters now
var report Report   // zero-value target for decoding
var findings []Finding // nil is a useful internal zero value

03

Names & contracts

A name is read where the code is called, not in isolation. Give the reader the missing context; do not repeat context they already have.

Strong conventions / Rules 02–07 · 16–20 · 34–35

Names should become shorter as their context becomes stronger.

Noise or ambiguity
const MAX_RETRIES = 3

type UserManager struct {
    running bool
}

func (u *UserManager) GetUserName() string
func (u *UserManager) FetchData() error
Context carries meaning
const MaxRetries = 3

type UserStore struct {
    isRunning bool
}

func (s *UserStore) Name() string
func (s *UserStore) FetchUser() error
  • Use MixedCaps or mixedCaps, including for constants. Keep initialisms in one case: XMLParser, xmlAPI.
  • Use short local names where the scope is tiny; use descriptive parameters on public functions and methods.
  • Avoid repeating package or type context: log.Info, not log.LogInfo.
  • Boolean prefixes such as is, has, and can are aids, not mandatory decoration. Established terms such as Enabled can be clearer.
  • Use receiver abbreviations consistently; avoid this, self, and long receiver names.
  • Avoid vague package names such as util, helper, or common. Name the capability.

Zero-value design

If a numeric enum has no natural zero state, reserve zero for Unknown or Invalid. If the domain really has a correct default, use it—do not manufacture a special placeholder value.

Comments state promises and explain why

A useful comment says which code is responsible, records constraints and reasons, or explains surprising behavior. It does not translate the next line into English.

Restates the operation
// Increment the retry count.
retries++
Preserves the reason
// Count the initial request as an attempt so the
// limit matches the value reported to operators.
retries++

Exported declarations need doc comments that stand alone in generated documentation. Error text normally starts lowercase and omits terminal punctuation because callers often compose it into a larger message. Use %q when whitespace or where a string begins and ends matters; use %s for ordinary prose. Prefer any to the legacy spelling interface{}.

04

Errors & failure

Errors are part of the API. Preserve information callers may need, say what operation failed, and choose where the program will log the error or show it to a user.

Strong conventions / Rules 20–24 · 29 · 34

Keep the cause available, and report the failure once.

Duplicate logging, cause hidden
data, err := store.Load(key)
if err != nil {
    slog.Error("Load failed", "err", err)
    return fmt.Errorf("Request failed: %v.", err)
}
return use(data)
Context once, chain intact
data, err := store.Load(key)
if err != nil {
    return fmt.Errorf("load %q: %w", key, err)
}
return use(data)
  • Return (T, error) or (T, bool); do not use an unexplained -1, empty string, or nil value to hide failure.
  • Handle the error first, return, and keep the successful path unindented.
  • Use %w when the underlying error should remain part of the API’s error chain, including when callers may need errors.Is or errors.As. Use %v when adding text without exposing that relationship; doing so deliberately ends the chain.
  • Normally either return an error with useful detail or report it to a user or operator. Logging and returning the same failure often produces duplicate messages.
  • Do not panic for expected input, network, storage, or request-time failures. A MustX helper is for a condition controlled by the programmer, usually at startup or in tests.

Where should an error be reported?

Helper packages should usually return errors and add useful detail. Report the error where the program must decide what happens next—for example, an HTTP handler that writes a response, a command that sets its exit status, or a supervisor that decides whether work can continue. Crossing into another package is not, by itself, a reason to log the error or hide its underlying cause.

Errors should carry the operation

return fmt.Errorf("decode deployment %q: %w", name, err)

if errors.Is(err, context.DeadlineExceeded) {
    // The caller can still decide what to do.
}

panic runs deferred calls while Go returns through the active function calls, a process often called stack unwinding. os.Exit and helpers such as log.Fatal do not. That distinction matters for cleanup, but neither is a substitute for an ordinary error path.

APIs & data

A good API makes correct use obvious, lets zero values work where practical, and exposes no more capability than the caller needs.

Strong conventions / Rules 25–27 · 30–33 · 35 · 38

Give callers only the operations they need.

A large interface defined by the implementation
type StorageClientInterface interface {
    Load(string) ([]byte, error)
    Store(string, []byte) error
    Delete(string) error
    Close() error
}

func NewClient() StorageClientInterface
A small interface defined beside its caller
// Defined beside the consumer that only reads.
type Loader interface {
    Load(string) ([]byte, error)
}

func NewClient() *Client
  • Keep interfaces small and usually define them where substitution is needed. Constructors normally return concrete types.
  • These are guidelines, not laws: a shared interface or interface-returning constructor can be correct when callers should not know which implementation is used.
  • Prefer an options struct for a long or ambiguous argument list. Functional options—functions passed to a constructor to adjust settings—can be useful when many settings are optional or likely to grow, but they add types, closures, and documentation.
  • Use channel direction in signatures so the compiler can enforce whether the function may send or receive.
  • Use any only when the operation truly accepts any type; prefer a concrete type or type parameter when it communicates more.

Do not copy locks

Do not copy synchronization values such as sync.Mutex or sync.WaitGroup after first use. Pass synchronization-bearing values by pointer.

Choose nil or empty slices according to the external format

Internally, a nil slice is a useful zero value: len, range, and append work. When data leaves the program, test the required representation. With encoding/json v1, nil becomes null and a non-nil empty slice becomes [].

var findings []Finding       // idiomatic internal zero value
results := []Result{}        // use when the JSON output must be []

func produce(out chan<- Event)
func consume(in <-chan Event)

Context & concurrency

Concurrent code is easier to maintain when its API shows who starts the work, who stops it, and how callers know it has finished.

Project convention / Rules 26–28 · 32 · 36 · 40–42

Every goroutine needs an evident end; work that affects correctness or shutdown also needs an explicit wait path.

Lifetime hidden
type Worker struct {
    ctx context.Context
}

func (w *Worker) Start() {
    go w.loop()
}
Lifetime in the call
func (w *Worker) Run(ctx context.Context) error {
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case job, ok := <-w.jobs:
            if !ok {
                return nil
            }
            w.process(job)
        }
    }
}
  • Put context.Context first. Pass it through the call chain; do not replace a caller’s context with context.Background().
  • Normally do not store a context in a struct because that hides lifetime. Compatibility adapters and operation-lifetime objects can justify an explicitly documented exception.
  • Document who closes channels, who waits for goroutines, and what cancellation means.
  • Avoid nested := when it accidentally shadows an outer value. Use = when replacing the existing context is the intent.
  • Prefer direct completion signals, cancellation assertions, or a WaitGroup over sleeping and hoping background work has finished.

Where a context begins

HTTP work starts from req.Context(); tests normally start from t.Context(); process entrypoints may begin with context.Background().

Avoid accidental shadowing

if needsTimeout {
    var cancel context.CancelFunc
    ctx, cancel = context.WithTimeout(ctx, 3*time.Second)
    defer cancel()
}

07

Tests as evidence

A good test does more than turn green. It states the behavior callers rely on, isolates the relevant cause, and fails with enough information to guide the repair.

Requirements and techniques / Rules 39–42

Make failures explain themselves, and check that work finishes.

Low-information failure
if got != want {
    t.Fatal("wrong result")
}
Failure includes the information needed to investigate
if got != want {
    t.Errorf(
        "Normalize(%q) = %q, want %q",
        input, got, want,
    )
}
  • Identify the operation and input; report got before want. For structured values, a readable diff is often better.
  • Use t.Fatal only when continuing the current test would be meaningless or unsafe. Otherwise collect independent evidence with t.Error.
  • Test helpers call t.Helper() so the reported line points to the caller.
  • Never call t.Fatal or t.FailNow from a worker goroutine; those stop only the current goroutine. Report with t.Error and return, or send an error to the test goroutine.
  • Use t.Context() as the test’s normal root context.
  • Use t.Parallel() only after proving the test does not share process state, ports, signals, mutable test data, or timing assumptions. Parallelism is an optimization.

Check that work really stops

Wait for an explicit completion signal where possible. testing/synctest is useful when code waits on timers or when a test must know that every goroutine in an isolated group is blocked. The optional goleak testing tool can find unexpected live goroutines when a direct completion check is impractical.

Choose a test that can reveal the particular bug

// Exact completion: wait for a completion signal or WaitGroup.
// Code that waits on time: consider testing/synctest.
// Data race: run the race detector.
// Allocation limit: use testing.AllocsPerRun.
// Busy-spin: use a fixed real timeout; the loop never blocks.

Teaching exceptions

go-crucible contains planted defects by design. The exception is narrow: preserve the mystery without teaching the wrong general lesson.

Exercise-authoring protocol

Describe the promised behavior; do not annotate the answer.

Starter code may violate the style or safety rule that the exercise teaches. Comments should still tell the learner what the component promises, who owns resources, and what external behavior matters—but should not name the planted violation, the faulty line, or the exact repair.

  • Starter implementation: one limited, realistic defect; no repair labels or comments that describe the solution.
  • Exercise README: enough background and symptoms to investigate without turning the task into transcription.
  • Hints: add evidence gradually, moving from the overall behavior to the responsible component and then the faulty operation.
  • Tests: idiomatic supporting code and a failure that demonstrates the broken behavior.
  • Solution: the repaired form follows this guide and explains why the limited change is sufficient.

Comment test

Would this comment let a learner identify the defect before observing or reasoning about it? If yes, move that information to a later hint or the solution explanation.

Leaks the repair
// Sort Findings by severity and name before encoding
// so JSON reports do not change order between runs.
return enc.Encode(report)
States only the promised behavior
// Findings use a stable order so stored reports
// remain useful in human and automated diffs.
return enc.Encode(report)

The second comment deliberately leaves a discrepancy between the promised behavior and the implementation for the learner to discover. In production code, once repaired, the comment may remain useful because it records the stable-order requirement without describing the old faulty line.

09

Worked reviews

Longer examples show how several small style decisions combine into code that is easier to operate and change. The domains resemble go-crucible, but the examples are independent illustrations—not copies of exercise implementations or solution patches.

Worked review A / alert configuration

Replace an ambiguous argument list with named configuration.

The anti-pattern compiles and may even look concise at its declaration. The cost appears everywhere it is called: three booleans and two durations cannot explain themselves, and adding one setting changes every caller.

Anti-pattern / arguments encode a memory test
type Evaluator struct {
    threshold    float64
    sendRecovery bool
    failOpen     bool
    repeat       bool
    window       time.Duration
    cooldown     time.Duration
}

func NewEvaluator(
    threshold float64,
    sendRecovery bool,
    failOpen bool,
    repeat bool,
    window time.Duration,
    cooldown time.Duration,
) *Evaluator {
    return &Evaluator{
        threshold:    threshold,
        sendRecovery: sendRecovery,
        failOpen:     failOpen,
        repeat:       repeat,
        window:       window,
        cooldown:     cooldown,
    }
}

e := NewEvaluator(0.95, true, false, true, 5*time.Minute, time.Hour)
Pattern / names make the call reviewable
type EvaluatorConfig struct {
    Threshold       float64
    SendRecovery    bool
    FailOpen        bool
    RepeatAlerts    bool
    EvaluationWindow time.Duration
    Cooldown         time.Duration
}

func NewEvaluator(cfg EvaluatorConfig) (*Evaluator, error) {
    if cfg.Threshold < 0 || cfg.Threshold > 1 {
        return nil, fmt.Errorf(
            "threshold %v is outside [0, 1]",
            cfg.Threshold,
        )
    }
    if cfg.EvaluationWindow <= 0 {
        return nil, errors.New("evaluation window must be positive")
    }

    return &Evaluator{cfg: cfg}, nil
}

e, err := NewEvaluator(EvaluatorConfig{
    Threshold:        0.95,
    SendRecovery:     true,
    RepeatAlerts:     true,
    EvaluationWindow: 5 * time.Minute,
    Cooldown:         time.Hour,
})

How a reviewer reasons about it

  • The configuration groups values that change for the same reason.
  • Field names expose the meaning of booleans where the constructor is called.
  • The constructor validates the configuration, so an invalid evaluator cannot enter the system.
  • The constructor returns an error because configuration can be invalid; a MustNewEvaluator wrapper would only be appropriate for programmer-owned static configuration.

Do not overapply

Two obvious arguments do not need a struct.

An options type has its own documentation and maintenance cost. Introduce one when it makes calls safer or future changes less disruptive.

Worked review B / audit report construction

Give business rules names so reviewers can check them.

The condensed version hides three business decisions inside a loop: which findings count, how severity is mapped, and when the report becomes unhealthy. The revision makes those decisions separately testable without inventing a framework.

Anti-pattern / business rules hidden inside the loop
func summarize(fs []Finding) Report {
    r := Report{}
    for _, f := range fs {
        if !f.Suppressed && f.Namespace != "dev" {
            r.Findings = append(r.Findings, f)
            if f.Severity == "critical" || f.Severity == "high" {
                r.Failed = true
            }
            r.Counts[strings.ToLower(f.Severity)]++
        }
    }
    return r
}
Pattern / business rules have names and types
type Severity string

const (
    SeverityUnknown  Severity = "unknown"
    SeverityLow      Severity = "low"
    SeverityHigh     Severity = "high"
    SeverityCritical Severity = "critical"
)

func summarize(findings []Finding) Report {
    report := Report{
        Counts: make(map[Severity]int),
    }

    for _, finding := range findings {
        if excludedFromReport(finding) {
            continue
        }

        report.Findings = append(report.Findings, finding)
        report.Counts[finding.Severity]++
        report.Failed = report.Failed || failsAudit(finding.Severity)
    }
    return report
}

func excludedFromReport(f Finding) bool {
    return f.Suppressed || f.Namespace == "dev"
}

func failsAudit(severity Severity) bool {
    return severity == SeverityHigh || severity == SeverityCritical
}

What changed—and what did not

  • A dedicated Severity type reduces accidental mixing with ordinary strings and centralizes the recognized values. External input still needs validation because Go permits other values through conversions and untyped string literals.
  • The helper names state the business rules and let tests address each rule directly.
  • The loop still reads top to bottom and uses ordinary language features.
  • The map is explicitly initialized because this function writes to it; the nil-slice zero value remains fine for Findings.

When to add a helper

Extract a rule when its name explains the decision.

Do not extract every comparison. A helper that merely renames an expression makes the reader jump elsewhere without learning anything.

Worked review C / reporting errors once

Return detailed errors; log once where the program decides the outcome.

When every function logs the same error, operators see several messages for one failure. Helper functions should return errors that say what they were doing. The HTTP handler, command entrypoint, or worker supervisor should decide how to report the failure and whether the program can continue.

Anti-pattern / every function logs the same failure
func loadRules(path string) ([]Rule, error) {
    data, err := os.ReadFile(path)
    if err != nil {
        slog.Error("read failed", "path", path, "err", err)
        return nil, err
    }

    var rules []Rule
    if err := yaml.Unmarshal(data, &rules); err != nil {
        slog.Error("parse failed", "path", path, "err", err)
        return nil, err
    }
    return rules, nil
}

func run(path string) error {
    rules, err := loadRules(path)
    if err != nil {
        slog.Error("startup failed", "err", err)
        return err
    }
    return serve(rules)
}
Pattern / context travels, reporting happens once
func loadRules(path string) ([]Rule, error) {
    data, err := os.ReadFile(path)
    if err != nil {
        return nil, fmt.Errorf("read rules %q: %w", path, err)
    }

    var rules []Rule
    if err := yaml.Unmarshal(data, &rules); err != nil {
        return nil, fmt.Errorf("parse rules %q: %w", path, err)
    }
    return rules, nil
}

func run(ctx context.Context, path string) error {
    rules, err := loadRules(path)
    if err != nil {
        return fmt.Errorf("initialize rule service: %w", err)
    }
    return serve(ctx, rules)
}

func execute(ctx context.Context, args []string) error {
    if len(args) != 1 {
        return errors.New("usage: rules-service RULES_FILE")
    }
    return run(ctx, args[0])
}

func main() {
    if err := execute(context.Background(), os.Args[1:]); err != nil {
        slog.Error("command failed", "err", err)
        os.Exit(1)
    }
}

Trace the resulting message

main receives one useful message: initialize rule service: parse rules "alerts.yaml": …. Because each function wrapped rather than replaced the error, callers can still use errors.Is and errors.As. Only main logs it, because only main decides the process exit status.

Result

One failure, one log entry, full detail.

The final log can still have structured fields. Do not repeat the same fact in both the message and a field unless a log query needs the field.

Worked review D / worker responsibility

Make responsibility for concurrency explicit.

A fire-and-forget method hides whether work can be cancelled, whether it is safe to call twice, and how shutdown knows completion occurred. A synchronous Run method lets the caller decide whether to place it in a goroutine and how to join it.

Anti-pattern / hidden goroutine and hidden stop path
type Refresher struct {
    interval time.Duration
    cache    *Cache
}

func (r *Refresher) Start() {
    go func() {
        ticker := time.NewTicker(r.interval)
        for range ticker.C {
            if err := r.cache.Refresh(); err != nil {
                slog.Error("refresh failed", "err", err)
            }
        }
    }()
}
Pattern / caller controls start and stop
type Refresher struct {
    interval time.Duration
    cache    *Cache
}

// Run refreshes the cache until ctx is cancelled.
// It returns only after releasing its timer.
func (r *Refresher) Run(ctx context.Context) error {
    ticker := time.NewTicker(r.interval)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-ticker.C:
            if err := r.cache.Refresh(ctx); err != nil {
                return fmt.Errorf("refresh cache: %w", err)
            }
        }
    }
}

// The supervisor owns concurrency and waits for Run to return.
group.Go(func() error {
    return refresher.Run(ctx)
})

The API now answers four questions

  • Who starts concurrency? The supervisor.
  • Who requests stop? The code that created and controls ctx.
  • Who releases the timer? Run, in the same frame that created it.
  • Who reports failure? Run returns it; the supervisor decides whether to retry, stop, or report it.

Design principle

Let the caller decide when to start a goroutine.

A lower-level Run method that blocks until it finishes is usually easier to combine, test, and stop cleanly.

Worked review E / behavior-focused tests

Test behavior with cases that explain each threshold.

The first test checks several facts but tells a future reader little about the input range. The table-driven revision names the thresholds and reports enough information to reproduce a failure.

Anti-pattern / assertions without a model
func TestSeverity(t *testing.T) {
    if classify(0.2) != SeverityLow {
        t.Fatal("bad")
    }
    if classify(0.8) != SeverityHigh {
        t.Fatal("bad")
    }
    if classify(1.0) != SeverityCritical {
        t.Fatal("bad")
    }
}
Pattern / named thresholds and useful failures
func TestClassify(t *testing.T) {
    tests := []struct {
        name  string
        value float64
        want  Severity
    }{
        {name: "below high threshold", value: 0.79, want: SeverityLow},
        {name: "at high threshold", value: 0.80, want: SeverityHigh},
        {name: "below critical threshold", value: 0.99, want: SeverityHigh},
        {name: "at critical threshold", value: 1.00, want: SeverityCritical},
    }

    for _, test := range tests {
        t.Run(test.name, func(t *testing.T) {
            got := classify(test.value)
            if got != test.want {
                t.Errorf(
                    "classify(%v) = %q, want %q",
                    test.value, got, test.want,
                )
            }
        })
    }
}

Why the extra lines earn their place

  • Case names document the thresholds as behavior, not implementation.
  • Values immediately below and at each threshold catch off-by-one errors.
  • got and want appear with the input, making CI output self-contained.
  • The subtests are not marked parallel: there is no demonstrated suite-time benefit, so parallelism would add no value here.

Test design

Together, the cases should explain the rule.

A table is useful when its rows show related parts of the input range. It is not automatically better than one focused test.

Production lens / readability during incidents

Code is read during incidents.

Production-minded style is not about predicting every outage. It is about making expensive questions easier to answer: who owns this work, how does it stop, what happens after partial failure, which resources must be released, what can operators inspect, and how much code a repair must change.

Read the production chapter

Keep production behavior simple.

Every extra moving part gives an operator more possible states to rule out. Add complexity only for a specific, measured benefit.

Show whether important promises are being kept.

If a timeout, retry, shutdown, or queue limit matters, expose enough information to check it and write a test that fails when the rule is broken.

Report each failure once.

Return errors until code must report them to a user or operator. Add searchable fields there and preserve the underlying error when callers can act on it.

Make repairs easy to limit.

Clear responsibilities let maintainers repair one component without first understanding the entire system.
